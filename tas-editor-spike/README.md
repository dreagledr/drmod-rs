# TAS Editor Spike (dear-imgui-rs)

Спайк, проверяющий **dear-imgui-rs** + **dear-imgui-cte** как замену провалившемуся
`windows-reactor` (`../tas-editor/`) для TAS-редактора. Это не редактор, а ответ на три
вопроса, от которых зависит выбор стека.

## Что проверялось

1. Тянет ли таблица **20 000 строк** с данными и редактируемыми ячейками — как в реальном
   редакторе, где скрипты доходят до 20 000 кадров (один кадр на строку, 30 колонок).
2. Годится ли `TextEditor` из `dear-imgui-cte` (ImGuiColorTextEdit) как редактор `.tas`-текста —
   включая **моноширинный шрифт** и **автодополнение**.
3. Стоит ли рантайм `dear-app` своей цены: докинг, тема, цикл кадра из коробки.
4. Годится ли `dear-file-browser` для рабочей папки и списка скриптов.
5. Можно ли автоматизировать UI тест-движком — **не получилось, см. «Тест-движок» ниже**.

## Шрифт и автодополнение

Оба — из `dear-imgui-cte`, оба проверены в работе (спайк печатает при старте, что именно встало).

- **Шрифт.** `dejavu_font_source(16.0)` отдаёт моноширинный DejaVu, вложенный в крейт
  (штатный `.ttf` не нужен). Добавляется в атлас как `FontAtlas::add_font(&[source]) -> FontId`.
  ⚠️ Делать это можно **только в `configure_imgui`** — рендерер забирает атлас себе после этого
  хука, и позже добавленный шрифт до экрана не доедет. В кадре шрифт пушится только вокруг
  редактора (`ui.push_font(id)` + `drop(token)`), таблица и подписи остаются шрифтом по умолчанию.
- **Автодополнение.** `TextEditor::set_autocomplete(&AutocompleteConfig::new(), callback)`;
  в колбэке `request.set_suggestions(...)` получает **29 имён токенов DSL** — словарь формата
  играют они, а не идентификаторы документа. Дефолты конфига: срабатывание по вводу (задержка
  200 мс) и по Ctrl+Space.
  У крейта есть и встроенный три (`enable_trie_autocomplete`), но он собирает идентификаторы
  **из самого документа** — для DSL это не тот словарь, поэтому взят свой список.

## Язык подсветки

Зарегистрировано **ровно 11 языков + «None»** — и добавить двенадцатый через публичный API
нельзя. Список лежит в C-API, который биндит Rust:

```
third-party/cimCTE/cimCTE.h:401-411   ← Language_C/Cpp/Cs/AngelScript/Lua/Python/Glsl/Hlsl/Json/Markdown/Sql
third-party/cimCTE/.../TextEditor.h:539      ← struct Language
third-party/cimCTE/.../TextEditor.cpp:11540-14037  ← реализации
```

⚠️ `struct Language` **имеет публичные поля** (`keywords`, `declarations`, `identifiers`,
`singleLineComment`, `isPunctuation`, `customTokenizer`), то есть **в C++ свой язык собрать
тривиально**. Но C-API отдаёт только 11 геттеров и `TextEditor_SetLanguage(const Language*)` —
ни конструктора, ни сеттера ключевых слов. Поэтому **из Rust свой `.tas` не зарегистрировать:
это форк зависимости, а не настройка.**

Что сделано вместо этого: стоит **`Language::Python`** — у него маркер однострочного
комментария ровно `#` (`TextEditor.cpp:13105`), как в `.tas` (`docs/SCRIPT_DSL.md` §1).
Ни один из 30 токенов DSL не совпадает с ключевыми словами Python, поэтому подсветка выходит
без ложных срабатываний: комментарии красятся, числа красятся, токены остаются обычными
идентификаторами. Оговорка: у Python включены `'`/`"` как строки — случайная кавычка в `.tas`
начнёт «строку».

По-настоящему свой язык делается **патчем `dear-imgui-cte-sys`**: он компилирует свой шим
(`shim/cte_bridge.cpp`) через `build.rs`, и туда достаточно добавить `const Language* Language_Tas()`
с заполненными полями — дальше существующий `TextEditor_SetLanguage` его примет.

## Рабочая папка и список скриптов

`dear-file-browser = "0.18"` — по умолчанию включены **оба** бэкенда (`native-rfd` и `imgui`).
Кнопка «Открыть папку…» вызывает `FileDialog::new(DialogMode::PickFolder).open_blocking()`,
дальше список `.tas` собирается своим `std::fs::read_dir` (расширение сверяется
без учёта регистра) — так же, как это делает C#-редактор.

Четыре вещи, которые здесь неочевидны:

- ⚠️ **`open_blocking` работает только на нативном бэкенде.** На `Backend::ImGui` он вернёт
  `Err(FileDialogError::Unsupported)` — внутрикадровый браузер это **другой** API
  (`FileDialogState` + `ui.file_browser().show(&mut state)`), его рисуют в кадре.
- ⚠️ **Отмена — это `Err(FileDialogError::Cancelled)`, а не пустой `Ok`.** Проверять надо
  отдельным вариантом, иначе отмена попадёт в ветку «ошибка».
- ⚠️ **Блокирующий диалог нельзя открывать с открытым кадром ImGui**, поэтому он вызывается
  из `Application::prepare_frame` — `dear-app` зовёт этот хук **до** того, как ImGui откроет
  следующий кадр. Кнопка только ставит флаг, диалог показывает следующий `prepare_frame`.
- ⚠️ **`rfd` показывается без родительского окна**: `dear-file-browser` в `to_rfd()` не зовёт
  `set_parent`, так что диалог не модален нашему окну и может оказаться позади него.
- ⚠️ **Пока диалог открыт, цикл кадра стоит** — это ожидаемая пауза, а не зависание
  (проверено вручную: паузы 1.9–3.5 с в логах прогонов — это и есть открытый диалог).
  Спайк подписывает её отдельно и **исключает из статистики кадров**: это время пользователя,
  и без исключения любой `max`/`avg` перестаёт что-либо значить. Всё, что длиннее 100 мс
  и диалогом **не** объяснено, печатается как `СТОП … — ничем не объяснён` — так настоящий
  стоп не спрячется за ожидаемым.

Список читается **по событию** (открытие папки, «Обновить»), а не в рендере, и ничего не
бросает: ошибка становится строкой в панели. Проверено — папка без `.tas` даёт «скриптов 0»,
несуществующая папка даёт `os error 3` строкой, и цикл кадра продолжается.

Папку можно задать заранее — так список проверяется без кликов по диалогу:

```bash
set SPIKE_FOLDER=E:\repo\drmod-rs\tools\demo&&cargo run
```

## Данные в таблице

Таблица и текст редактора — **проекции одного сегмента** `SEGMENT` (`src/main.rs`), как в
настоящем редакторе: таблица реализует текст в кадры. Сегмент повторяется каждые 300 кадров
до 20 000; левый стик занят почти каждый кадр, кнопки лежат окнами поверх — так выглядит
настоящий TAS, а не решётка из пустых ячеек. Все 20 000 строк непусты.

- **Колонка стика** (`ls` / `lsx` / `lsy` / `rsx` …) — текстом: у стика значение числовое.
  В кадре занята ровно одна из трёх форм стика (`docs/SCRIPT_DSL.md` §4).
- **Колонка кнопки** (`a`, `x`, `lt`, `lr` …) — **чекбоксом** (`ui.checkbox`). Он
  **редактируемый**: клик меняет флаг в данных строки.
- ⚠️ Правка квадратика **не переписывает текст** редактора — обратная запись «кадры → текст»
  в спайке не сделана. Счётчики правок над таблицей это показывают.

## Флажки: цвет вместо галочки

Колонки кнопок рисуются **закрашенным квадратом** (зелёный — нажато, красный — отпущено),
а не галочкой: `ui.checkbox` убран, вместо него `invisible_button` для клика плюс заливка.
Переключается переменной, чтобы сравнивать:

| `SPIKE_FLAGS` | Как выглядит |
|---|---|
| _(не задана)_ / `square` | маленький квадрат `14×14` по месту ячейки (`get_window_draw_list().add_rect(..).filled(true)`) |
| `cell` | заливка **всей ячейки** цветом состояния (`table_set_cell_bg_color`) — цветная «сетка» получается сама |

**Производительность одинаковая: 0.48 ms/кадр в обоих режимах** (release, 20 000 × 30),
поэтому выбор чисто визуальный. Наблюдение при просмотре: в режиме `cell` соседние
удерживаемые кадры сливаются в сплошную полосу, и длину удержания видно глазом; в режиме
`square` клетка остаётся нейтральной и читается именно как чекбокс.

Цвета — `FLAG_ON` / `FLAG_OFF` в `src/main.rs`, размер — `FLAG_SIZE`.

## Как смотреть результат без скриншотов рантайма

У `dear-app` нет фичи `capture` (`test-engine = ["dep:dear-imgui-test-engine"]` — и всё),
поэтому скриншот из самого рантайма не снять: он требует `TestRunner::run_graphical`
со своим циклом кадра. Вместо этого окно снимается **снаружи**, скриптом
`.qwen/tmp/shot.ps1`: он находит окно по имени процесса, делает его активным и копирует
**только его прямоугольник** (`GetWindowRect` + `CopyFromScreen`) — рабочий стол в кадр
не попадает. Так дизайн проверяется глазами, не отказываясь от рантайма `dear-app`.

## Тест-движок: пробовали и убрали

`dear-imgui-test-engine` (0.18) подключался через фичу `dear-app/test-engine` ради автокликов
по виджетам — единственного, что не проверить вручную. **Убран: в этом рантайме движок не видит
ни одного айтема, включая кнопку в самом верху окна.**

Как это выглядит (`set_log_to_tty(true)` — лог движка идёт в stdout):

```
[0004] Error 'Unable to locate item: 'Spike app/##0-a' (0x00000000)'
[0362] Error 'Timed out waiting for item to be visible: 'Открыть папку…''
```

Что при этом **работало** (проверено): сам движок стартует и привязывается к контексту,
скрипт-тесты регистрируются и выполняются, нативные тесты движка регистрируются, его окна
рисуются, логи читаются, поиск по дикой маске включается. Не работало ровно одно — обнаружение
айтемов.

⚠️ **Важно:** провал прогона ≠ «клик не сработал». Успех надо проверять по
`count_tested > 0 && count_success == count_tested`; `Ok` от прогона этого не значит.

### Где причина (по исходникам, две независимые)

1. **`imgui_test_engine` — вырезана строка включения хуков** (`imgui_te_engine.cpp:1539`):

   ```c
   static void ImGuiTestEngine_UpdateHooks(ImGuiTestEngine* engine) {
       bool want_hooking = false;
       //if (engine->TestContext != nullptr)     // ← ЗАКОММЕНТИРОВАНО
       //    want_hooking = true;
       if (engine->InfoTasks.Size > 0)                  want_hooking = true;
       if (engine->FindByLabelTask.InSuffix != nullptr) want_hooking = true;
       if (engine->GatherTask.InParentID != 0)          want_hooking = true;
       ui_ctx->TestEngineHookItems = want_hooking;
   }
   ```

   Хуки айтемов вызываются только при `g.TestEngineHookItems`
   (`imgui_internal.h`: `IMGUI_TEST_ENGINE_ITEM_ADD/ITEM_INFO`). Флаг остаётся `false`, пока
   не поставлена одна из трёх задач, — то есть обычный `ItemClick` айтемы не видит.

2. **`dear-app` не вызывает `PreNewFrame`/`PostNewFrame`.** В референсном
   `app_minimal_main.cpp` кадр устроен как `NewFrame → Draw → ShowTestEngineWindows →
   PreSwap → PostSwap`, а цепочка `dear-app` (`.dear-app/src/runtime/surface.rs`) зовёт только
   `pre_swap`/`post_swap`. `PreNewFrame` не зовётся **нигде** ни в `dear-app`, ни в
   `dear-imgui-test-engine` — а это тот хук, на котором движок готовит сбор айтемов кадра.
   (⚠️ Второе — сильная корреляция, но не доказано экспериментом: `PreNewFrame` нельзя
   дёрнуть из публичного API `dear-app`, чтобы проверить.)

Эксперимент с дикой маской (`"**/Открыть папку…"`) закрыл первую часть: `Wildcard matching..`
шло 900 кадров с **включёнными** хуками — и айтем всё равно не нашёлся. То есть одной вырезанной
строки недостаточно, обе причины работают вместе.

### Если возвращаться к автокликам

Чинится не у нас: нужен либо вызов `PreNewFrame`/`PostNewFrame` из `dear-app`, либо правка
upstream-движка. Обе правки — в чужом коде, поэтому тему закрыли как «в этом стеке не работает»,
а не как «мы не разобрались». Отчёт в upstream не отправлялся.

## Сборка и запуск

```bash
cargo run
```

Спайк сам себя измеряет и завершает — иначе прогон невоспроизводим:

| Переменная | Действие |
|---|---|
| `SPIKE_SECONDS=10` | выйти через 10 с, печатая раз в секунду реальный интервал между кадрами |
| `SPIKE_NO_CLIPPER=1` | рисовать все 20 000 строк вместо видимого диапазона (`ListClipper`) |
| `SPIKE_FOLDER=<путь>` | задать рабочую папку до запуска — список проверяется без кликов по диалогу |
| `SPIKE_FLAGS=cell` | заливать всю ячейку цветом состояния вместо квадрата |

```bash
set SPIKE_SECONDS=10&&cargo run
set SPIKE_SECONDS=10&&set SPIKE_NO_CLIPPER=1&&cargo run
```

Vsync выключен (`PresentMode::AutoNoVsync`): с ним интервал между кадрами упирается в 60 Гц
и ничего не измеряет.

## Результаты (измерено 2026-09-28)

Интервал между кадрами, **20 000 строк × 30 колонок, данные заполнены, ячейки-чекбоксы,
моноширинный шрифт и автодополнение включены**:

| Режим | Release |
|---|---|
| **С клиппером** (`ListClipper`) | **0.47 ms/кадр (2130 fps)** |
| **Без клиппера** (все 20 000 строк) | 49.67 ms/кадр (20 fps) |

Разница — **≈97×** (аппаратно разброс прогон к прогону: 0.46–0.51 ms). Виртуализация здесь
не оптимизация, а условие работоспособности: без неё один кадр таблицы стоит дороже, чем весь
остальной UI.

Заполнение данными, чекбоксы, шрифт и автодополнение почти бесплатны — на пустых ячейках
с клиппером было 0.46 ms/кадр. В Debug те же величины: ~2.5 ms с клиппером против 333 ms
без него.

Прочее:

- **Версии:** `dear-app` / `dear-imgui-rs` / `dear-imgui-cte` — 0.18.0 (релизный поезд 2026-09-15).
  Крейты жёстко связаны версией: смешивать поезда нельзя.
- **Сборка:** собирается штатной цепочкой без C++-обвязки и без CMake — `build.rs` компилирует
  Dear ImGui C++ через `cc`. Первая сборка ≈73 с, зависимости скачиваются один раз.
- **Бинарник:** 9.87 МБ, один самодостаточный x64 exe без внешних DLL
  (для сравнения: C#-версия упаковывается в zip ≈75 МБ).
- **Требуется x64:** свой `.cargo/config.toml`, потому что корневой форсит i686.

## Чего этот спайк не проверяет

- **Настоящую подсветку `.tas`.** Стоит `Language::Python` как приближение (совпадает маркер
  комментария `#`), но сами токены DSL остаются обычными идентификаторами: ключевые слова
  Python — это не `ls`/`lt`/`wk`. Свой язык требует патча `dear-imgui-cte-sys` (см. «Язык подсветки»).
- **Сам выбор папки в диалоге.** Нативный диалог (`rfd`) не открыть и не закрыть в
  автоматическом прогоне: проверены сборка, вызов, пауза на время показа и все пути **после**
  диалога (успех, отмена, ошибка), и вручную он открывался. Но сценарий «выбрал папку → список
  обновился» headless не воспроизводится — список проверяется через `SPIKE_FOLDER`.
- **Парсер `.tas`.** Выбранный файл целиком уезжает в редактор (`set_text`), но таблица
  по-прежнему показывает синтетический `SEGMENT`: разбор текста в кадры не написан, а именно
  он нужен, чтобы таблица стала проекцией открытого файла.
- **Обратную запись правок** «кадры → текст» (см. выше).
- **Реальное удобство ввода** (каретка, выделение, undo, IME) — это оценивается глазами в окне,
  а не числами. Спайк доказывает лишь то, что редактор создаётся, рисуется и отдаёт текст
  (`set_text`/`text`) без ошибок.
