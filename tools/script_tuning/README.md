# script_tuning — поиск надёжного перелёта через барьер (core-скрипт 117)

Инструмент ищет тайминги скрипта, при которых Raiden **надёжно** перелетает
барьер 20 м в P310_RESTART, вместо того чтобы воспроизводить запись 117
побайтово.

## Откуда взялось ядро

Запись 117 (618 кадров) генерирует 360 команд, из которых осмысленных — семь.
Проверено по кадрам (биты `InputUnit`, см. `out/_tmp117/flight.py`):

| Кадр | Длит. | Ввод | Наблюдение |
|------|-------|------|------------|
| 40 | 5 | `forward` | разгон |
| 45 | 6 | `forward`+`jump` | апекс `pos_y` 1.67 на fi 61-62 |
| 51-75 | 25 | `forward` | падение до 0.33 |
| 76 | 6 | `forward`+`heavy_attack` | атака при `y` 0.51 — «почти у земли» |
| 96 | — | — | **лаунч**: +0.41/кадр, `velocity_y == 0` |
| 104 | 1 | `ripper` (keybind 11) | старт лаунча — на 8 кадров раньше |
| 165 | — | — | пик `pos_y` **24.20** |
| 234 | — | — | посадка, (−5.90, 39.05) |

Ключевое: лаунч стартует за 8 кадров **до** риппера, а `velocity_y` остаётся
нулём — высоту даёт root motion анимации тяжёлой атаки, приземлившейся в момент
касания земли. Риппер к высоте отношения не имеет.

Что выброшено: 175 однокадровых команд камеры с битом `right 0x100000`
(fi 131-558) и шумовые `backward`/`left` на fi 191 и fi 238-284. Камера на
перелёт не влияла: за весь полёт `cam_yaw` ушёл 2.90 → 3.12, `rot_y` не
менялся вообще, а `|Δyaw|` между записью и плейбэками < 1°
(`out/desync_cam_117.png`, панель 2).

## Файлы

- `core117.py` — сборка очищенного скрипта: `--jump`, `--attack`, `--ripper`,
  `--end`. Разгон до прыжка всегда 5 кадров (как в записи), поэтому сдвиг
  `t_jump` не превращает длину разгона в третью переменную.
- `sweep.py` — сетка `t_jump × t_attack`, генерация JSON-вариантов и (с `--run`)
  прогон через HTTP API с замером `max_y`. Рестарт миссии делает сам (полем
  `restart` в запросе), человека в цикле не требует.
- `drmod_api.py` — общий клиент API: HTTP на **блокирующем** сокете (сокет с
  таймаутом теряет ответ — `WinError 10053` в ~2/3 случаев; пустой ответ сервера
  тоже ретраится) и активация окна игры (игра опрашивает клавиатуру только когда
  окно в фокусе). `setup_stdout()` — UTF-8 + построчная буферизация вывода
  инструментов: иначе в логе кракозябры, а `→`/`≥`/`✓` роняют печать.
- `restart.py` — CLI рестарта миссии через меню паузы (`--up/--down`, `--dry`).
- `fail_recovery.py` — выход из fail-меню (игрок убит): с `--wait` сначала даёт
  умереть, затем жмёт `confirm` по «Retry» и печатает траекторию статусов.
- `run_json.py` — прогон JSON-скрипта из `test_inputs/` с печатью фаз и сводки.
- `menu_probe.py` — живой пробник меню: гоняет любую последовательность вводов
  (`pause`, `confirm`, `dik:0xC8`, `raw:8C`, `stick_down`) и печатает траекторию
  `menu_status`/поданных битов/позиции из `GET /logs`.
- `parry_geometry.py` — геометрия парирования/подброса: N прогонов связки,
  кадр удара (по `fed_down_bits`), кадр парирования (враг `anim 1114113`) и кадр
  подброса, корреляции с `post_gain` (подъём сверх высоты парирования) плюс
  оконный CSV `parry ± кадры` с выравниванием по событию. `--analyse` считает
  корреляции по готовым CSV, не трогая игру.
- `pg_pivot.py` — кадровые срезы окна парирования по прогонам: что было за
  кадры до контакта и в самом контакте (проверка, не держится ли корреляция на
  одном выбросе).
- `geometry_report.py` — сводка по run-CSV всех серий кампании одной таблицей:
  прогоны, парирования, перелёты, разброс `post_gain`, угол клинка в контакте и
  дистанция в момент удара (`py -3 tools\script_tuning\geometry_report.py "out/pg_n*.csv"`).
- `ab_runs.py` — **чередующийся** прогон нескольких вариантов связки в одной
  сессии (A/B/C/D через прогон, порядок вращается). Нужен потому, что серии,
  снятые по отдельности, расходятся между собой сильнее эффекта варианта: одна и
  та же связка дала 2/8 и 5/8 парирований. Варианты — JSON'ом в `--arm`
  (ключи = параметры `core117.build`), на выходе CSV с колонкой `arm` и сводка.
  Для сеток есть режим карты: `--grid jump=36:40 --grid attack=66:76:2 --base
  '{...}'` берёт произведение осей поверх общей связки, `--dry` показывает
  варианты без прогона. С фиксированным шагом времени (`--fixed-dt`) каждая
  ячейка воспроизводится, поэтому хватает 2 прогонов вместо 5–15.
- `timing_tune.py` — **перебор таймингов в детерминированном мире**: `POST /rng
  {"pin":"freeze","seed":S}` (заморозка LCG решений ИИ, см. `docs/API.md` §3.10)
  + `trigger: {"ticks": 0}` (старт ровно на первом тике геймплея, §3.3) и таблица
  «кадр атаки → `max_y`» с повторами лучшего варианта. В таком мире прогон
  воспроизводится бит-в-бит, поэтому тайминги подбираются осмысленно:
  `py -3 tools\script_tuning\timing_tune.py --seed 1 --trigger-ticks 0
  --attacks 76,78,79,80,82 --ripper 112`. Неудачный рестарт («loading не
  наступил») раннер ловит за `--rearm-wait` (14 с без фазы `running`), снимает
  скрипт и повторяет — иначе прогон пустой.
- `selftest.py` — оффлайн-проверка того, что не требует игры: допуски
  `in_zone` (зеркало `segment::in_zone`) и метрики перелёта.
- `order.py` — **заказ смены подфазы** через `POST /order` (скип катсцены
  штатной функцией движка): `py -3 tools\script_tuning\order.py P370_EVENT`
  (по умолчанию снимает `STA_EVENT`, иначе внутри события заказ игнорируется),
  `--no-clear-event` — без снятия, `--arg N` — аргумент заявки (по умолчанию 1).
  Печатает траекторию `/state` после заказа.
- `order_on_event.py` — то же, но **автоматически в момент старта сцены**: ждёт
  `STA_EVENT` вне паузы и сразу заказывает (`py -3 -u
  tools\script_tuning\order_on_event.py P370_EVENT --timeout 900`). Так был
  выполнен скип монолога: `P370_IN → P370_EVENT` (катсцена до боя).
- `subphase_now.py` — чтение текущей и чекпойнт-подфаз из глобалов игры
  (`base + 0x14B9140`): phase id, хэш подфазы, имя. Механика фаз, таблицы подфаз
  и что НЕ работает — `docs/PHASE.md`.
- `cutscene_skip.py` — **консольное меню скипа катсцены для in-engine сцены**:
  пока идёт заданная подфаза (по умолчанию `P370_IN` — монолог Монсуна), держит
  выставленными флаги `STA_SOFT_EVENT` + `STA_SOFT_EVENT_SKIP_OK` (коды 4 и 37),
  от которых Esc открывает **консольное катсценное меню** (`Cutscene Pause`), и
  как только в нём нажат confirm (бит 0x10 в `InputUnit.buttons_pressed`, подача
  — как у `confirm` в скрипте), заказывает `--next` (по умолчанию `P370_EVENT`,
  катсцена до боя) через `POST /order` с `clear_event`, после чего закрывает
  меню. Проверено живьём 2026-09-12: меню открылось как `Cutscene Pause`, после
  confirm игра ушла в `P370_EVENT`. Клавиатурный `Esc` инструмент **транслирует
  в pause-бит движка**: игра маппит Esc в бит `0x100` (`InputUnit.down`), но
  «фронта» (`pressed`) для клавиатуры не выставляет, а движковая проверка паузы
  в событии хочет именно фронт — поэтому без трансляции Esc консольное меню не
  открывается (обычный путь паузы при `STA_SOFT_EVENT` обрывается). Опрос — 50 Гц
  (короткое отпускание Esc не проспать). По завершении (после скипа или выхода из
  сцены) инструмент снимает свои флаги — катсценное меню не остаётся включённым
  в следующих сценах. Запуск: `py -3 -u
  tools\script_tuning\cutscene_skip.py [--watch P370_IN] [--next P370_EVENT]`.

## Прежде чем гонять

1. Игра запущена, мод заинжекчен, `GET /health` отвечает.
2. Миссия **P310_RESTART** (или другая — тогда поправьте `SPAWN` в `core117.py`).
3. Окно игры **не** трогать во время прогона: фаза рестарта требует фокуса, а
   курсор меню ходит клавишами `DirectInput` (см. §10.5 в `docs/API.md`).
   `sweep.py --run` активирует окно сам.
4. Проверить оффлайн-часть: `py -3 tools\script_tuning\selftest.py`.

## Порядок прогона — рестарт и взвод одним запросом

С 2026-09-10 рестарт миссии делается скриптом: в теле `POST /script/run`
появляется поле `restart` (`{}` — дефолты), и мод сам

1. отыгрывает меню паузы (`pause` → стрелка **вверх** → `confirm` ×2 — пункт
   Restart нижний, и он открывает диалог подтверждения с выбранным YES);
2. ждёт фактического loading новой миссии;
3. взводит скрипт по `trigger` — по `pos` (зона спавна) или по `ticks` (N тиков
   геймплея после загрузки), см. `docs/API.md` §3.3.

Одним скриптом это делается потому, что активный скрипт в моде ровно один
(второй `POST /script/run` → `409`). Взводить, стоя на спавне, по-прежнему
нельзя — но с `restart` это не проблема: взвод происходит **после** loading,
когда позиция уже новая.

⚠️ Для воспроизводимости триггер лучше **тиковый**: позиционный срабатывает на
0–1-м тике после загрузки (плюс-минус тик), сдвиг старта на тик меняет фазу
врага, и один и тот же конфиг давал 25.4–26.8 м (враг появлялся на кадре
74/73/77 вместо 75). С `"trigger": {"ticks": 0}` старт привязан к тикам
симуляции — фаза одинаковая, прогоны совпадают бит-в-бит (см. «Воспроизводимый
прогон»). Конец прогона ждать по `GET /script/{id}` (статус `done`/`stopped`):
в `/state` запись скрипта **остаётся** после завершения, и ожидание «пока
`script` не станет null» висит до таймаута (прогон ~10–15 с, а не минута).

**Шаг 0 — базовая точка.** Первым делом прогоните вариант, воспроизводящий
запись (`j45 a76`). Если он не даёт ~24 м, значит скриптовый путь расходится с
записью так же, как плейбэки, и двигать тайминги бессмысленно — сначала надо
чинить подачу ввода.

```
py -3 tools\script_tuning\core117.py out\tuning\baseline.json --pretty
py -3 tools\script_tuning\run_json.py out\tuning\baseline.json --focus
```

**Шаг 1 — грубая сетка** (15 вариантов, ~5 минут вместе с перезапусками):

```
py -3 tools\script_tuning\sweep.py --run
```

**Шаг 2 — точный перебор** вокруг лучшего результата, шаг 1 кадр:

```
py -3 tools\script_tuning\sweep.py --run --step 1 --jump 44:46 --attack 74:80
```

**Шаг 3 — надёжность.** Победителя прогнать 3-5 раз подряд:

```
py -3 tools\script_tuning\sweep.py --run --repeat 3 --step 1 --jump 45:45 --attack 76:76
```

Без `--run` утилита только раскладывает варианты в `out\tuning\*.json` —
их можно запускать вручную (`run_json.py`, `POST /script/run` или `test_api.ps1`).

## Подброс: механика, тайминги и адаптивный удар (2026-09-11)

Перелёт барьера даёт **не разбег, а парирование прыжка врага**. По записи 142:
тяжёлая атака нажата на кадре 77, когда игрок ещё в воздухе (`y≈0.72`, анимация
игрока 94), враг переходит `anim 19 → 1114113` на кадре 99 (дистанция 0.67 м), и
игрока поднимает до 22.1 м на кадре 167. Наземная атака (анимация 81) не
парирует: удар приходит, когда игрок уже приземлился.

Что даёт фиксированные тайминги (все прогоны — рестарт скриптом, `spawn_ok=1`):

| серия | разгон / бег в полёте | jump | attack | t_run | прогонов | лаунч |
|---|---|---|---|---|---|---|
| `out/tuning2` | 5 / вперёд | 44:46 | 72:78 | связан | 21 | 3 (до 34.8 м) |
| `out/tuning3` | 5 / вперёд | 45:47 | 74:77 | связан | 36 (3×) | 4 |
| `out/tuning5/t36` | 2 / пауза | 45 | 74:75 | 36 | 20 (10×) | 4 (до 29.5 м) |
| `out/tuning5/t38` | 2 / пауза | 45 | 74:75 | 38 | 20 | 1 |
| `out/tuning5/t40` | 2 / пауза | 45 | 74:75 | 40 | 20 | 4 (до 29.9 м) |

Надёжность фиксированных таймингов — **5–20%**, распределение бимодальное
(23–35 м или 2–3 м): решает состояние врага, а оно между прогонами плавает (та же
недетерминированность, что в десинк-анализе). Поэтому основной путь —
**адаптивный удар**: поле `when_enemy` у команды (см. `docs/API.md` §4.1) —
команда спит, пока враг не окажется в нужной анимации/кадре/дистанции:

```
py -3 tools\script_tuning\core117.py out\tuning\adaptive.json --run-frames 2 --t-run 36 \
   --attack-when-enemy "{\"anim\": [65545, 19], \"frame_max\": 60, \"dist_max\": 2.5}"
py -3 tools\script_tuning\run_json.py out\tuning\adaptive.json --focus --restart
```

Проверка гипотезы на живых прогонах: `probe_enemy_runs.py` (N прогонов одного
варианта с выгрузкой таймлайна врага и `max_y` каждого) — по нему подбираются
`anim`/`frame_max`/`dist_max` для `when_enemy`.

## Геометрия парирования: что решает подброс (2026-09-11)

Гипотеза «треугольника» (высота игрока — высота клинка врага — дистанция)
проверена двумя сериями, 30 и 40 прогонов (`parry_geometry.py`; разбор кадровых
срезов — `pg_pivot.py`).

Твёрдо установлено:

* **Подброс бывает только от парирования** (враг уходит в `anim 1114113`): в
  серии 40 парирований 8, и все 8 дали подъём на 6.2–21.6 м выше высоты
  парирования (`post_gain`). Прогоны без парирования — только прыжок (1.6–3.5 м).
* **Высота клинка в момент парирования постоянна**: `blade_y ≈ 3.0` м во всех
  прогонах (анимация врага), то есть переменных в треугольнике две — высота
  игрока и дистанция. `enemy_frame == 0` на кадре парирования — выравнивание
  точное.
* **Прыжок врага стартует вместе с нашим ударом**: в кадре подачи удара враг уже
  в `anim 65545` с кадром 0–7 и в 4–4.8 м. То есть на **управляемом** моменте
  (нажатие удара) парирование не предсказывается: у парирований и промахов
  одинаковые `y` (0.49–0.71), `vy` (−0.11…−0.14) и дистанция. Контакт приходит
  на 18–22 кадра позже — в конце прыжка врага (кадр 28–36 анимации 65545).

Что **не** воспроизводится — сила подброса. В серии 40 она коррелирует с высотой
игрока в момент парирования (r=+0.89: `y≥2.7` → 13.7–21.6 м, `y≈2.4` → 6.2–10.3 м),
но в серии 30 лучшие подбросы (25.1 и 22.9 м) случились при `y` 2.39–2.54 — ниже,
чем посредственные в серии 40. Дистанция в момент парирования даёт разный знак
корреляции (r=−0.63 и r=+0.70), а на кадре парирования она ещё и загрязнена
сменой анимации врага (за 2 кадра до контакта 0.21 м, в кадре контакта 1.12 м).
Вывод: при n≈8–11 устойчив только сам факт «парирование → подброс», а величина
подброса решается фазой контакта с точностью до кадра — предсказать её по
измеряемой геометрии этими сериями не удалось.

## Сдвиг удара по кадру прыжка врага (2026-09-11)

Попытка отодвинуть удар относительно прыжка врага (`frame_min` в `when_enemy`)
вскрыла важное: **условие сдвигает команду только раньше штатного `t`**. При
`frame_min 8` и `14` (гейт `player_y` 0.3–0.8 остался) удар в **16 прогонах из
16** прошёл ровно на кадре `t = 76`, при `враг_кадр` 0–9 (условие требовало ≥ 8)
и `игрок_y ≈ 0` (гейт требовал ≥ 0.3) — условие не выполнялось ни разу, а удар
был: сработал запасной `t`. В контроле (`frame_min 0`) удары шли на 69–73 — там
условие выполнялось.

Что это дало по числам (8 прогонов на вариант):

| вариант | подача удара | парирований | `max_y` | `post_gain` |
|---|---|---|---|---|
| `frame_min 0`, y 0.3–0.8 | 69–73 (по условию) | 2/8 | 19.0 / 19.3 | 16.3 / 16.5 |
| `frame_min 8` | 76 (штатный `t`) | 2/8 | **31.1 / 31.2** | 28.3 / 28.6 |
| `frame_min 14` | 76 (штатный `t`) | 1/8 | 30.2 | 27.5 |

То есть сравнение вышло не «ранний против позднего по врагу», а «удар по условию
(69–73) против штатного кадра записи (76)» — и выиграл 76 (n=2–3 на плечо,
тонко). Чтобы сдвигать удар по врагу по-настоящему, штатный `t` надо двигать
вместе с `frame_min` (или снять гейт по `player_y`, тогда условие работает как
задержка); это и проверяется серией с `--attack 84` и `--attack-when-enemy
"{\"anim\":[65545],\"frame_min\":N}"`.

⚠️ При сдвиге удара вправо проверьте **риппер**: его кадр (104 в записи) должен
быть вне удержания атаки. При `--attack 84 --attack-duration 24` окно атаки
(84..108) накрывает 104, и `core117.build` раньше выбрасывал команду риппера
**молча** — серия с такими параметрами шла без риппера (обнаружено 2026-09-11).
Теперь это `ValueError` с подсказкой: сдвиньте `ripper` (≥ `attack + dur`) или
уменьшите `dur_attack`.

## Ninja run и «стоп в воздухе» (2026-09-11)

До этого ninja run в связке не подавался вообще — в игре была видна обычная
пробежка, а не ninja run. Связка по ручной технике: разгон **с ninja run** →
прыжок с ним же (другая анимация, чем без него) → **стоп в воздухе** (отпустить
`forward`+`ninja_run`) → `forward + ninja_run + тяжёлая атака`. В скрипте это
`--ninja` (бит 0x4000 + удержание keybind 8 на всех командах) плюс
`--release-tail N` (зазор без ввода перед атакой — «стоп»). Пилот, 8 прогонов на
вариант:

| связка (ninja везде) | удар | стоп | парирований | ≥20 м | `post_gain` |
|---|---|---|---|---|---|
| ninja | 76 | 0 | 4/8 | 0/8 | 3.1 / 1.1 / 5.2 / 10.6 |
| **ninja** | **76** | **6** | **5/8** | **4/8** | 18.3 / 26.2 / 22.3 / 29.9 / 10.3 |
| ninja | 70 | 6 | 1/8 | 0/8 | 6.1 |
| ninja | 70 | 0 | 5/8 | 0/8 | 0.1–1.0 |

Что видно: ninja run сам по себе поднимает долю парирований (4–5 из 8), но без
стопа подброс слабый (проносит мимо врага — та же «касательная», что в серии
l00). Стоп перед атакой даёт и парирования, и сильный подброс (в 4 из 8 прогонов
`max_y` 20.6–33.0). Удар на 70 — поздно по фазе контакта: парирования есть, а
подброса нет вовсе (0.1–1.0 м). Совпадает с геометрией: сильные подбросы идут,
когда контакт приходится на кадры 95–99 при игроке на высоте 2.5–3.1 м.

Длина стопа (сводка `geometry_report.py`, все — ninja + удар 76):

| стоп | парирований | ≥20 м | угол клинка в контакте |
|---|---|---|---|
| 0 | 4/8 | 0/8 | 40–74° (проносит мимо, удар «по касательной») |
| 6 | 6/14 (43%) | **4/14 (29%)** | −9…27° |
| 10 | 5/20 (25%) | 3/20 (15%) | −1…18° |
| 14 | 7/20 (35%) | **5/20 (25%)** | −2…34° |
| 18 | 4/8 | 0/8 | 62–71° (контакт отодвинут, клинок приходит сверху) |
| 6 + разгон 3 | 2/8 | 2/8 | −3…18° |

То есть ninja run удлиняет разгон и без стопа игрока проносит за врага: контакт
приходится на клинок сзади/сверху (угол 40–74°) и вверх-назад вместо
вверх-вперёд. Рабочая зона стопа — 6–14 (ниже 0/18 подбросов нет), внутри неё
серии уже не различить при n=8–20 — разброс между сериями больше эффекта.

Отдельно — `--no-ninja-flight`: ninja держится только на разгоне и прыжке, в
полёте остаётся один `forward` (прыжок при этом ninja-овый), на удар ninja
включается снова. Это проверка ручной гипотезы «после начала прыжка отпустить
ninja run и держать только вперёд: анимация прыжка как на бегу, но скорость
меньше», вместе с ранним прыжком (`--jump 41/43` вместо 45) — ninja удлиняет
разгон, и прыжок, возможно, надо начинать раньше.

Обе гипотезы проверены **чередующимся** прогоном (`ab_runs.py`: варианты идут
через прогон, 8 на вариант) — так дрейф сессии бьёт по всем вариантам одинаково:

| вариант (стоп 6, удар 76) | парирований | ≥20 м | `post_gain` |
|---|---|---|---|
| jump 45, ninja держится | 3/8 | 2/8 | 10.0–27.6 |
| jump 41, ninja держится | 4/8 | 3/8 | 9.6–27.7 |
| jump 45, ninja отпущен | 5/8 | 1/8 | 12.1–25.4 |
| **jump 41, ninja отпущен** | **5/8** | **5/8** | **20.3–29.2** |

Ключевое здесь не 5/8, а то, что у последнего варианта **все парирования дали
перелёт** (минимум 20.3 м), тогда как у соседних часть парирований давала только
10–16 м. То есть ранний прыжок вместе с отпусканием ninja в полёте убирает
«слабые» парирования — парирование становится достаточным условием перелёта.

⚠️ **Повтор той же серии (`ab_runs.py`, 15 прогонов на вариант) этот вывод не
подтвердил:** `j41-nf` дал **0/15** парирований (при том, что `j45-n` держал свои
5/15), а его удар в этой сессии приходился на землю (`y(удар) ≈ 0` вместо
0.13–0.79). То есть ранний прыжок с отпущенным ninja — хрупкая связка: она не
гарантирует, что удар придёт в воздухе, а от этого и зависит парирование. При
этом и у `j45-n` в той же серии три парирования из пяти дали всего 0.1–0.5 м.
Вывод по методике: при n≈8–15 и таком разбросе варианты сравнимы только внутри
одной серии (что и делает `ab_runs.py`), но и этого мало — воспроизводимость
между сессиями проверять обязательно, одиночная серия ничего не доказывает.

## Эталонный рецепт (2026-09-11)

Связка, которая даёт и парирование, и перелёт, и не зависит от FPS:

```
core117.build(jump=39, run_frames=6, attack=<по умолчанию 76>, dur_attack=24,
              ripper=104, release_tail=6, ninja=True, ninja_flight=False,
              attack_when_enemy={"player_y_min": 0.01, "player_y_max": 0.25,
                                 "player_vy_max": 0.0})
```

Через CLI то же самое:

```
py -3 tools\script_tuning\parry_geometry.py --runs 15 --jump 39 --release-tail 6 \
   --ninja --no-ninja-flight \
   --attack-when-enemy "{\"player_y_min\":0.01,\"player_y_max\":0.25,\"player_vy_max\":0.0}"
```

Или тем же набором параметров в `ab_runs.py` (чередующийся прогон, колонка `arm`):

```
py -3 tools\script_tuning\ab_runs.py --runs 15 --out out\ab_ref.csv --arm "{\"name\":\"ref\",\"jump\":39,\"release_tail\":6,\"ninja\":true,\"ninja_flight\":false,\"attack_when_enemy\":{\"player_y_min\":0.01,\"player_y_max\":0.25,\"player_vy_max\":0.0}}"
```

Замер (15 прогонов, чередующийся прогон `ab_runs.py`, миссия P310_RESTART):

| | значение |
|---|---|
| парирований | **7/15 (47%)** |
| перелётов ≥20 м | **7/15 (47%)** — все парирования дали перелёт (`max_y` 21.6–32.7 м) |
| `post_gain` | 19.2–30.1 м |
| высота игрока в кадре удара | 0.13–0.24 (окно триггера) |
| суммарно по 4 сериям (30 прогонов) | парирований 17/30 (57%), перелётов 14/30 (47%) |

Почему так:

- **ninja run** (`--ninja`) — без него другие анимации прыжка и удара в воздухе;
- **`ninja_flight=False`** — после прыжка ninja отпускается, в полёте только
  `forward`: скорость меньше, а анимация прыжка остаётся «как на бегу»;
- **`release_tail=6`** — «стоп в воздухе» перед атакой (без стопа игрока проносит
  за врага, клинок приходит сзади/сверху — подброс вверх-назад);
- **триггер по высоте 0.01–0.25 на спуске** — удар подаётся, когда игрок почти у
  земли. Это условие проверяется по **состоянию игры**, а не по кадру отрисовки,
  поэтому оно не зависит от FPS: кадр скрипта 76 при 43–57 FPS попадал то в
  воздух, то на землю, а триггер находит момент контакта в каждом прогоне сам.

Числа — отправная точка, а не истина: кадр прыжка (38–41), длина стопа (5–10) и
края окна высоты сдвигаются без потери связки (прыжки 38/40 дали 2/5 перелётов,
41 — 3/5; стоп 8 и 10 — 0/5 и 2/5 при n=5). Проверять изменения — только
чередующимся прогоном внутри одной сессии (`ab_runs.py`) и повторять серию: при
n≈5–15 одиночная серия ничего не доказывает.

### После переноса тика в физику (2026-09-11)

Кадр скрипта теперь равен тику симуляции (см. `QWEN.md`, `docs/API.md` §4.1:
ввод подаётся из детура `updateInputUnit` через очередь кадров, как replay), и это
сразу видно по цифрам: в фиксированной связке (без триггера) высота игрока в кадре
удара стала **монотонной функцией тика удара** — 0.73 при 66, 0.35 при 74, ≈0 при
76 (раньше разъезжалась от −0.01 до 0.57 и путала все серии):

| тик удара | парирований | ≥20 м | `post_gain` | высота в удар |
|---|---|---|---|---|
| 66 | 3/4 | 0/4 | 0.2–0.5 | 0.70–0.98 |
| 68 | 2/4 | 0/4 | 0.1–1.1 | 0.58–0.77 |
| 70 | 1/4 | 0/4 | 3.1 | 0.29–0.61 |
| 72 | 2/4 | 0/4 | 12.3–17.0 | 0.25–0.66 |
| 74 | 1/4 | 1/4 | 30.8 | 0.13–0.35 |
| 76 | 0/4 | 0/4 | — | ≈ 0 (на земле) |

Смысл: чем позже удар, тем ниже игрок в контакте и тем вертикальнее подброс
(0.2 → 12 → 30.8 м), но удар перестаёт попадать в прыжок врага (на 76 — уже на
земле и не даёт ничего). Триггер по высоте как раз ловит позднюю зону в каждом
прогоне.

Оптимум оказался **плато, а не точкой**: после правки тика прогнаны окна
(0.01–0.25 / 0.05–0.30 / 0.10–0.35 / 0.15–0.40) и ручки (стоп 4/6/8,
`dur_attack` 20/24/28) — все варианты дают одинаковый результат в пределах шума
(1–3 парирования из 5, подбросы 15–30 м). Сводка по 60 прогонам после правки с
триггером: **парирований 43% (26/60), перелётов ≥20 м 35% (21/60)**.

## Фиксированный шаг времени движка (2026-09-11)

Причина, по которой одинаковые серии расходились, нашлась в движке:
`cSlowRateManager` (`base + 0x17E93B0`) держит **измеренную** длительность кадра в
`m_fTickDifference` (`+0x8C`, миллисекунды) — живой разброс 16.25–19.25 мс при
номинале 16.667, то есть те самые 52–61 FPS, — и коэффициент `m_fTickRate`
(`+0x7C`) = `diff / 16.667`, который читают анимация и кинематика. Смещения
сверены с дизассемблером `startup`/`setTickDelay` и подтверждены зондом
(`out/peek_time.py` читает память игры снаружи, мод не трогая):

```
tickRate +0x7C = 1.005 … 1.155      (коэффициент кадра)
ticks    +0x80 = растёт ~1000/с     (накопленное время, мс)
tickDiff +0x8C = 16.25 … 19.25      ← дельта кадра
```

Мод умеет подменять её номиналом: `POST /dt {"fixed": true}` (по умолчанию
выключено, состояние — в `/state` → `dt`), из инструментов — `api.fixed_dt(True)`
или `ab_runs.py --fixed-dt`. Пишет хук обновителя кадра `updateFrameTime`
(`0xA03970`) **после оригинала**, то есть до потребителей кадра: `tickDiff` =
16.667, `tickRate` = 1.0, `unit[0].m_fDelta` = 1.0 и часы `ticks` (+0x80) —
линейно, `база + N·16.667` за кадр (опция `ticks: false` оставляет дельту, но
возвращает часы на реальный dt — A/B). Замер чтением памяти: при `ticks: true`
`ticks` растёт ровно на 16.666 мс за кадр, при `false` — на реальные ~22.4;
темп символьного времени 0.82 от реального, т.е. **игра замедляется**, а окно
замедления риппера составляет ровно 60 кадров при любом FPS.

Что это даёт на практике (та же сетка фиксированного удара, что раньше
разъезжалась):

| тик удара | высота игрока в удар (без фикс. dt) | с фикс. dt |
|---|---|---|
| 70 | 0.29–0.61 | **1.015 / 1.015** |
| 72 | 0.25–0.66 | **0.945 / 0.945** |
| 74 | 0.13–0.35 | **0.834 ×3** |
| 76 | ≈ 0 (на земле) | **0.684 / 0.684** |

То есть без флага один и тот же тик давал разброс в треть метра, с флагом —
побитово одинаковую высоту. Побочные следствия: (1) вертикальная динамика
прыжка/падения дельту использует, поэтому после включения флага все тайминги
сдвигаются (кадр 76 больше не «на земле», а на 0.684) — связку надо
перенастраивать в детерминированном мире; (2) при реальном FPS ниже 60 игровое
время идёт медленнее реального; (3) выключение возвращает измеренную дельту.

## Воспроизводимый прогон: заморозка RNG + тиковый триггер (2026-09-12)

Второй источник разброса после часов — **решения ИИ врага**: он бросает
глобальный LCG (`base + 0x19D0814`, функции `0x9DE2A0`/`0x9DE2D0`/`0x9DE300`), и
от выпавшего значения зависит, прыгнет он на игрока (парирование → подброс) или
нет. 15 сайтов ИИ бросают этот RNG; старт его прыжка плавал 73–81 и с HP игрока
не коррелировал.

`POST /rng` (`docs/API.md` §3.10) даёт рычаг:

- `{"pin":"freeze","seed":N}` — состояние LCG **замораживается** на первом тике
  скрипта: каждый вызов возвращает детерминированную функцию своих аргументов
  (порядок бросков между потоками перестаёт влиять), поведение остаётся «живым» —
  в отличие от константного пина (`lo/mid/hi`), который убирает случайность
  вместе с прыжком врага;
- вместе с `"trigger":{"ticks":0}` (§3.3) одинаковый конфиг воспроизводится
  **бит-в-бит**, а исход выбирается сидом.

Пере-настройка таймингов в детерминированном мире (`freeze seed 1`, `ticks=0`,
`jump=39, run_frames=6, dur_attack=24, ripper=112, release_tail=6, ninja=True,
ninja_flight=False`):

| атака@ | 76 | 78 | 79 | **80** | 82+ |
|---|---|---|---|---|---|
| `max_y` | 11.90 | 21.48 | 28.27 | **32.69** | 1.06 (удар опаздывает) |

**Эталон:** `freeze seed 1` + `trigger.ticks=0` + `jump=39, attack=80,
dur_attack=24, ripper=112, release_tail=6, ninja=True, ninja_flight=False` →
`max_y` **32.69 м**; 5 прогонов (1 + 4 повтора) совпали бит-в-бит (прыжок врага
75, HP врага 121). `attack@79` даёт 28.27 м — тоже 5/5 идентичных.

```
py -3 tools\script_tuning\timing_tune.py --seed 1 --trigger-ticks 0 \
    --attacks 80 --ripper 112 --repeat-best 4
```

Что это меняет для прежних серий: раньше «надёжность» связки была 5–20% и её
мерили сериями по 8–15 прогонов (`ab_runs.py`). Теперь при фиксированном сиде
прогон не «попадает», а воспроизводится — подбирать надо сид (перебор `--seed`)
и кадр атаки. Кадр риппера — тоже ручка: тот же `attack@79` с `ripper=104` даёт
21.42 м, а с `ripper=112` — 28.27 м.

## Рестарт: как это работает и что смотреть

Рестарт делается полем `restart` (см. выше) — человека в цикле нет. Если что-то
не срабатывает, порядок диагностики:

1. `py -3 tools\script_tuning\restart.py` — рестарт отдельным скриптом (без
   полёта): видно переходы `menu_status` (`Pause Menu → NONE → In Game`) и
   вердикт «рестарт выполнен / не подтверждён».
2. `py -3 tools\script_tuning\menu_probe.py pause dik:0xC8 confirm confirm` —
   вручную отыграть ту же последовательность и посмотреть кадры в `/logs`.
3. В `debug.log` мода есть строки `api: script N '...' restart phase ...`,
   `restart done -> armed (loading=true)` и (если рестарт не сработал)
   `рестарт не сработал: loading не наступил`. Плюс диагностика ввода:
   `menu: press isKeyDown(0x8C)=1 при статусе 3` (игра увидела клавишу в меню) и
   `keys: ms_InputKeys[0xD0] down (DIK)` (наш DIK-бит лёг в сырое состояние).

**Mission Fail (игрок убит)** — отдельный случай: игра сама из fail-меню не
выходит, а в этом состоянии каждый прогон получает «игра не в геймплее». Поэтому
`ensure_gameplay` (и `drmod_api.recover_fail`) на статус из `FAIL_STATUSES`
жмёт `confirm` (в fail-меню выбран Retry) и ждёт `In Game` — проверено живьём
2026-09-11: `Mission Fail → In Game`, ~1 с. Диагностика вручную:

```
py -3 tools\script_tuning\fail_recovery.py --wait 0      # если уже в fail-меню
py -3 tools\script_tuning\fail_recovery.py --wait 420    # дать умереть и выйти
```

Типичные причины «не двигается курсор»: окно игры не в фокусе (главная —
игра опрашивает клавиатуру только в foreground), `open_gap` слишком мал (стрелка
приходит в анимацию открытия меню), в меню другой порядок пунктов (тогда
поправьте `ups`/`downs` в `restart`).

**С титула (свежий запуск игры)** сейв поднимается другой последовательностью:
сначала START, затем подтверждения — `menu_probe.py pause dik:0x1C dik:0xD0
dik:0x1C dik:0x1C` (START → CONTINUE → слот 2 → загрузка → подтверждение).
Простой `dik:0x1C …` без START остаётся на титуле (состояние `In Menu`, игрок не
найден — по `/state` это видно сразу). Проверено 2026-09-12: у титула и экрана
слотов работает **мод-канал** (`menu_probe.py confirm`, `down`, `confirm` —
титул CONTINUE → слот → диалог авто-сейва → загрузка), а настоящие клавиши через
Win32 `keybd_event` игра на фронтенде **не принимает** — навигацию делать
мод-каналом. Ориентир по экрану: подпись внизу (`Enter CONFIRM`, `Esc BACK`),
диалог авто-сейва подтверждается тем же `confirm`.

⚠️ Известный риск: на одном прогоне игра крашнулась сразу после выбора Restart,
до загрузки миссии (после перехода на ожидание loading и фокус окна не
