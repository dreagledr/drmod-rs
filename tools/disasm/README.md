# Дизассемблирование (инструменты)

PowerShell-скрипты для диагностики игровых механик через чтение кода игры. Принцип: **сначала дизассемблировать, потом хукать** — это оказалось в разы эффективнее эмпирических тестов (см. `docs/REPLAY_FINDINGS.md`, секция «Ripper / Blade Mode»).

## scan_calls.ps1

Найти call site функции по RVA. Сканирует exe на диске (ищет `call rel32` → target RVA) и, опционально, память запущенной игры (релоцированные абсолютные адреса).

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools/disasm/scan_calls.ps1 -Rva 0x785190
powershell -NoProfile -ExecutionPolicy Bypass -File tools/disasm/scan_calls.ps1 -Rva 0x785190 -Mem
```

## dump.ps1

Hex dump диапазона кода (для ручного дизассемблирования вокруг call site).

```
powershell -NoProfile -ExecutionPolicy Bypass -File tools/disasm/dump.ps1 -Rva 0x810400 -Len 0x380
```

## Порядок работы

1. Определить целевую функцию (например, из SDK: `enableRipperMode` @ `base + 0x785190`).
2. `scan_calls.ps1 -Rva 0x785190` → список call site (RVA).
3. `dump.ps1 -Rva <call_site - 0x20> -Len 0x100` → hex байтов.
4. Дизассемблировать вручную: `cmp`/`test` + `jz`/`jnz` перед `call` = условие активации.

## Проверенные факты (2026-08-16)

- base игры = `0x00370000` (релокация), ImageBase exe = `0x00400000`.
- В exe на диске абсолютные адреса функций = `ImageBase + RVA` (`0x400000 + RVA`), в памяти = `base + RVA` (`0x370000 + RVA`); `call rel32` (E8) не релоцируется (относительный).
- `enableRipperMode` (0x785190) вызывается из RVA `0x8106BD`/`0x8106D0`; условие: `canActivateRipperMode() && isKeybindPressed(11)`.
- `disableRipperMode` (0x7D9590) — из `0x81053D` и др.
- `isKeybindDown` @ 0x61D280 (→ `isKeyDown` 0x9D93A0), `isKeybindPressed` @ 0x61D2D0 (→ `isKeyPressed` 0x9D9400).
- `vtable[209]` = `canActivateRipperMode` (`mov edx, [eax+0x344]`; 209*4 = 0x344).

## ⚠️ Адреса: файл ≠ память (проверено 2026-09-11)

`dump.ps1`/`scan_calls.ps1 -Mem` читают **память процесса**, поэтому абсолютные
адреса в их выводе уже с релокацией. В файле на диске те же адреса меньше на
`base − 0x400000` — **а base меняется от запуска к запуску** (2026-08-16 было
`0x370000`, 2026-09-11 — `0x930000`). Поэтому:

- адрес из вывода `dump.ps1` нельзя искать в файле как есть: сначала вычесть
  `base − ImageBase` (для запуска 2026-09-11 это `−0x530000`);
- `scan_calls.ps1` (без `-Mem`) и `py -3 out\scan_addr.py` работают по файлу —
  туда подставляйте именно файловые значения;
- `call rel32` (E8) от релокации не зависит — его можно искать в файле напрямую.

## Модуль времени движка (найден 2026-09-11)

RVA (файловые, ImageBase 0x400000):

| RVA | Что |
|---|---|
| `0x9F8110` | init: `timeBeginPeriod(1)`, `QueryPerformanceFrequency` → `0x2304F20`, старт QPC → `0x2304F18`, флаг `0x2304F40`, «секунд на тик» → `0x2304F14` |
| `0x9F81A0` | stop: `timeEndPeriod(1)`, сброс флага |
| `0x9F81D0` | время в секундах: `(QPC − старт) × секунд_на_тик` (округление через f32) |
| `0x9F8230` | сырые тики QPC с момента старта (edx:eax) |
| `0x9F8260` | «секунд на тик» |
| `0x9F8270` | тики → секунды (аргументы на стеке) |

Глобалы (адреса **runtime**, как в выводе `dump.ps1`): старт QPC `0x2304F18`,
частота `0x2304F20`, секунд на тик `0x2304F14`, флаг `0x2304F40`. Прямых `call`
к геттерам нет — они вызываются **косвенно (через vtable)**, поэтому потребители
(в т.ч. планировщик шагов симуляции) находятся только хуком геттера или через
vtable-таблицы.

Измерено рантаймом (2026-09-11): **число вызовов `updateInputUnit` в секунду не
зависит от дельты кадра** (58.6–58.9 при 16.667…21 мс и без фиксации), при этом
игра тикает чаще, чем рисует (≈58.7 против 51 FPS) — то есть шаги добираются
аккумулятором по собственному времени, а не по нашей дельте. `updateInputUnit`
зовётся **четырьмя вызовами подряд** (по одному на слот ввода, `user_index` 0–3,
буферы `0x020AB850+0x30*i`) из функции `0x61E8A0`; её вызывают обёртки
`0x64A4CC`, `0x64D13C`, `0x64F5D9` под флагами вида `test [0x0211A060], 0x8000`.

`Pl0000::enableRipperMode` (0x785190) ставит `m_bRipperModeEnabled` (+0x3184 = 1) и
запускает эффекты, но `cSlowRateManager` не трогает — секундное замедление от
риппера включается не в активации, а в обновлении сцены/мира, которое читает
состояние риппера.

## Кто вызывает геттер времени (хук `input_hooks::create_time_hook`, 2026-09-11)

Хук на `getTicks` (0x9F8230) пишет адреса возврата вызывающих (naked-детур:
адрес берётся из стека до кадра компилятора, затем хвостовой `jmp` в трамплин).
Снимок виден в `GET /state` → `time_callers` (там же RVA = адрес − база модуля).
Замер в меню паузы:

| RVA | вызовов/с | что это |
|---|---|---|
| `0xB980B7` | ~13 600 | внутри цикла кадра: `Sleep((остаток)/3)` + повторный замер — **пацер кадров** (игра сама держит кап ~60 FPS) |
| `0xB98008` | ~118 (≈2/кадр) | измерение времени кадра |
| `0x9F2A57`, `0x9F2A6A` | ~34 | разовые потребители |

То есть горячие чтения времени — это ограничитель FPS, а не планировщик шагов;
аккумулятор (если он есть) ищется среди редких вызывающих.

⚠️ Частоту вызовов ввода/шагов надо мерить **в геймплее**: в меню у функции
`0x61E8A0` работает другая ветка (вызовы `0x9DAFC0` вместо `updateInputUnit`), и
цифры из меню про шаги ничего не говорят.

## Как движок считает время (измерено 2026-09-11)

Часы движка (`m_fTicks`, `cSlowRateManager + 0x80`, мс) идут **ровно в ногу с
реальным временем** (темп 0.999–1.010 при 58.5 FPS): `m_fTickDifference` — это
измеренная длительность кадра (16.6–20.6 мс в геймплее), и `m_fTicks += diff`
каждый кадр. То есть «пропуск кадров» из описания игры — это variable-dt
компенсация: симуляция проматывается на реальную дельту, а не на 1/60.

Следствие для подброса от риппера (он считается по символьному времени за
«медленную секунду» ≈ `кадры × дельта`): без фиксации при 58.5 FPS за секунду
набирается ровно 1000 мс, с фиксацией 16.667 — только 975 мс (−2.5%), и подброс
падает; потолок — 60 × 16.667 = 1000 мс. Значит фиксировать надо дельту ≈
реальной (17–19 мс при 58.5 FPS), а не номинал.

Замер часов — `py -3 out\clock_rate.py` (внешнее чтение памяти, мод не трогает).

## Попытка синтетических часов и почему геттер не подходит (2026-09-11)

Идея «вариант 2»: отдавать символьное время счётчиком (`шаг × 16.667 мс`), чтобы
шаг был абсолютно стабильным, а при нехватке FPS игра замедлялась (TAS-подход).
Реализовано в моде (`POST /dt {"steps": true}`), но:

- **все** зарегистрированные вызывающие сырого геттера `getTicks` — это пацеры
  кадров (`0xB980B7`/`0xB98008` — спин `Sleep(остаток/3)`; `0x9F2A57`/`0x9F2A6A` —
  замер кадра и `Sleep(вычисленное)`), а им нужны РЕАЛЬНЫЕ часы;
- выдача синтетики пацеру вешает игру (он засыпает/крутится на «замёрзшем»
  времени) — наблюдали краш 2026-09-11;
- значит через геттер время симуляции не перехватить: оно идёт через
  `cSlowRateManager::m_fTickDifference` (его мод и так фиксирует) и реальное
  накопление (`m_fTicks`, которое растёт 1:1 с реальным временем).

Следующая точка вставки — **писатель `m_fTickDifference`** (`cSlowRateManager+0x8C`;
файловый адрес поля для запуска с base 0x930000 — `0x01BE943C`, искать
`py -3 out\scan_addr.py 0x01BE943C`), а не геттер времени.

## Ровная сетка кадров через хук `Sleep` (2026-09-11)

Подброс зависит от числа кадров за окно замедления риппера (`кадры × дельта`),
поэтому плавание FPS переносится в результат. Идея: встать на `Sleep` и выдавать
**пацерам** игры задержку до дедлайна жёсткой сетки — тогда число кадров в
секунду постоянно.

Реализовано: `create_sleep_hook` (адрес `Sleep` берётся из слота IAT игры,
`SLEEP_IAT_RVA = 0x11FD1BC`; для запуска с base 0x930000 это значение `0x754CD730`
— системный адрес, проверяется порогом `SYSTEM_ADDR_MIN`), детур `sleep_detour`
(stdcall, naked) отдаёт задержку решателю `pacer_sleep_ms`, а тот для вызывающих
`PACER_SLEEP_CALLERS` (`0xB980B2`, `0x9F2A8E`) считает время до дедлайна сетки.
Включается через `POST /dt {"fps": 50}` (0 — выключить), состояние — в
`/state` → `dt.limit`/`limit_fps`.

⚠️ Состояние на конец 2026-09-11: хук встаёт на верный `Sleep`, но **включение
сетки не проверено** — пост с полем `fps` не доходил до ответа, а `limit`
остаётся выключенным. Первым делом проверить: чтение частоты QPC
(`TIME_QPF_RVA = 0x19D4F20`) — при нуле `set_frame_limit` сам себя выключает, —
и не блокируется ли обработчик (логирование из HTTP-потока уже убрано).
