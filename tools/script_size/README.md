# script_size — замер размера скриптов

Считает, сколько байт занимает скрипт в трёх представлениях (JSON
`POST /script/run`, текст `.tas`, таблица команд), как он сжимается и сколько
памяти занимает кольцевой буфер логов.

Код мода не трогается: лимиты и схемы берутся из `src/api.rs` и
`replay-types/src/script.rs` (см. §«Откуда цифры»).

## Запуск

```bash
python tools/script_size/measure.py                    # отчёт + примеры (~35 с: сжатие часа логов)
python tools/script_size/measure.py --frames 3600      # без замера часа логов (быстро)
python tools/script_size/measure.py --gen              # только сгенерировать примеры
python tools/script_size/measure.py --file <скрипт>    # посчитать готовый .json/.tas
python tools/script_size/measure.py --high-effort      # gzip 9, zstd 19, brotli 11 (медленно)
python tools/script_size/measure.py --out <каталог>    # переопределить каталог примеров

python tools/script_size/check_gzip_e2e.py             # сквозная проверка приёма gzip (§ ниже)
```

Требуется `zstandard` (и, для brotli, `brotli`):

```bash
python -m pip install zstandard brotli
```

⚠️ Вывод сгенерированных отчётов — на русском (как и `measure.py`), поэтому в
`cmd.exe` с кодовой страницей 1251 он падает на `UnicodeEncodeError`; запускать
из UTF-8-консоли (`chcp 65001`) или из `pwsh`.

## Приём gzip: сквозная проверка

`check_gzip_e2e.py` поднимает локальный сервер, повторяющий путь чтения тела из
`src/api.rs` (`Content-Length` + `Content-Encoding` → `gunzip_limited` → `parse_script`),
и проверяет контракт транспорта на скрипте длиннее старого потолка:

| Проверка | Ожидание |
|----------|----------|
| plain JSON 5000 кадров (304 КиБ) | `413 body too large` — в 64 КиБ не влезает |
| тот же скрипт под gzip (16 КиБ) | `200` + `total_frames: 5000` |
| битый gzip | `400` |
| `Content-Encoding: br` | `415` |
| zip-бомба (128 МиБ → 127 КиБ на проводе) | `413 body too large` (в лимит тела не влезла) |

⚠️ Мод отвечает `413` **до** чтения тела, поэтому невычитанные байты дают `RST`; клиент
проверки это глотает (ответ уже получен). Живой мод проверяется так же — тем же
скриптом, но против `127.0.0.1:5223`.

## Что получается

- `report.md` под корнем тула — таблицы со всеми цифрами (генерируется).
- `examples/` — те же скрипты отдельными файлами: `<профиль>.json` и
  `<профиль>.tas`, чтобы их можно было подать в мод или редактор.

⚠️ И `report.md`, и `examples/` — **сгенерированные** и в git не лежат
(`.gitignore`): `logs_<кадры>.json` на часе это ~162 МиБ, а всё остальное
пересоздаётся одним запуском.

| Файл | Что это |
|------|---------|
| `benign.json` / `.tas` | бег по кругу (по 60 кадров на угол), редкие нажатия + «рестарт-хвост» меню-клавишами (стрелка вверх + confirm) |
| `rotsplit.json` / `.tas` | худший случай по числу команд: каждый кадр — своя команда (стик гуляет каждый кадр) |
| `sticky.json` / `.tas` | мало команд на длинный прогон: один стик на треть скрипта |
| `restart_heavy.json` / `.tas` | 4 рестарта в одной фазе (команды `restart` строит сам мод) |
| `logs_3600.json` | **ответ `GET /logs`**, не скрипт: 3600 кадров кольцевого буфера по схеме `LogFrameJson` |
| `logs_216000.json` | то же ×60 (60 запросов подряд) |

`--file` принимает готовый `.json`/`.tas` (в т. ч. выгрузку `tools/dbdump
--script` или эталон из `tas-editor-cs/TasEditorCs.Tests/Fixtures/`) и считает
уже его. С `--file` замер логов не делается.

## Почему «час» меряется тактами

Отчёт считает размер **одного такта** (3600 кадров = 60 с) и умножает на число
тактов. Такт — это удобная единица: столько кадров помещается в кольцевой
буфер логов (`RING_CAPACITY`) и столько же был прежний потолок скрипта.
Скрипт же теперь длиннее такта (см. ниже) — но замер на такте остаётся
корректным, потому что размер скрипта линеен по числу кадров: строка на кадр
в тексте, команда на кадр в JSON.

Буфер логов на час истории не рассчитан: старые кадры вытесняются. Час логов —
это 60 выборок `GET /logs?limit=3600`, а память буфера остаётся постоянной.

## Сколько теперь влезает

Потолок в 3600 кадров снят (осталась страховка `MAX_SCRIPT_FRAMES` =
1 000 000), и ограничитель — **размер тела запроса**. С приёмом
`Content-Encoding: gzip` (лимит тела считается по сжатым байтам) предел стал
таким:

| Профиль | Кодек | КиБ на кадр | Влезает в 64 КиБ | Длительность при 60 FPS |
|---------|-------|-------------|------------------|-------------------------|
| `rotsplit` (команда на каждый кадр — худший случай) | gzip | 3.44 B | ≈ **19 000 кадров** | ≈ **5.3 мин** |
| `rotsplit` | plain | 65.2 B | ≈ 1 000 кадров | ≈ 17 с |
| `benign` (бег с редкими нажатиями) | gzip | 0.31 B | ≈ 209 000 кадров | ≈ 58 мин |
| `benign` | plain | 2.31 B | ≈ 28 000 кадров | ≈ 7.9 мин |

То есть «гуляющий стик каждый кадр» и тот влезает на ~5 минут сплошного прогона
вместо прежних 60 секунд, а обычный скрипт — почти на час. Цифры перепроверяются
`fits_check.py` (тот же расчёт: `лимит / (байт на кадр)`).

## Откуда цифры

| Величина | Источник |
|----------|----------|
| `MAX_BODY_BYTES` = 65536 | `src/api.rs` (лимит тела `POST /script/run`) |
| `RING_CAPACITY` = 3600 | `src/api.rs` (60 FPS × 60 с) |
| `MAX_LOG_LIMIT` = 5000 | `src/api.rs` (максимум кадров в ответе `/logs`) |
| `MAX_SCRIPT_FRAMES` = 1 000 000 | `replay-types/src/script.rs` (верхняя страховка; практический ограничитель — лимит тела) |
| `LOG_FRAME_BYTES` = 216 | размер `LogFrame` в памяти, пришпилен тестом `api::ring_tests::log_frame_stays_216_bytes` в `src/api.rs`; падение теста = цифру здесь и в `measure.py` надо пересчитать |
| схема кадра скрипта | `ScriptCommand` / `ScriptInput` (`replay-types/src/script.rs`), `deny_unknown_fields` + `skip_serializing_if` |
| схема кадра лога | `LogFrameJson` / `InputJson` (`src/api.rs`); `decode_buttons` отдаёт не более 10 имён |
| синтаксис `.tas` | `docs/SCRIPT_DSL.md` §3–§5 (канонический `Write`) |
| реальный порядок размеров команд | `tools/dbdump --script` на живой записи (`docs/SCRIPT_DSL.md` §9) |

## Оговорки

- Байты лога — **оценка сверху**: сериализатор мода печатает `f32` с
  минимально достаточной точностью (как `serde_json`), харнесс — кратчайшую
  round-trip форму; порядок величин совпадает, точная дельта в пределах
  процентов.
- `LOG_FRAME_BYTES` — измеренная величина; если поля `LogFrame` изменятся,
  цифру памяти нужно переизмерить.
- `restart_heavy` показывает не размер скрипта, а отсутствие отдельного лимита
  на размер `restart`-фазы (≈0.8 КиБ + `tail` кадров на рестарт).
- Уровни сжатия по умолчанию практичные (gzip 9, zstd 3, brotli 5): максимум
  (zstd 19, brotli 11) на часе логов считается десятки минут, а разница —
  проценты. «Сколько бы сжал лучший кодек» — флаг `--high-effort`.
- Сжатие скрипта — не потолок выигрыша, а текущее поведение транспорта: мод
  принимает `Content-Encoding: gzip` и считает лимит тела по сжатым байтам
  (`src/api.rs`), поэтому `gzip`-колонка отчёта — это то, что реально влезает
  в 64 КиБ. Ответы (`GET /logs`) мод не сжимает — там цифры остаются оценкой
  выигрыша.
