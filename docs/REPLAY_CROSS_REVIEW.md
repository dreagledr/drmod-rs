# Оценка: коррекция расхождений при воспроизведении только через ввод

## Краткий диагноз (по вашим данным)

Из FINDINGS следует три раздельных источника расхождения:

1. **Переменная дельта времени анимации/кинематики.** Физика — fixed-step (vel.y совпадает побайтово), но горизонтальное движение и поворот интегрируются с реальным dt. При FPS 52–58 последовательность dt ≠ записи → дрейф `rot.y` уже на i≈50–55, позиция следом. Косвенное подтверждение: рост FPS с ~52 до ~58.5 снизил playback↔playback разброс в ~13× (21 м → 1.63 м).
2. **Реконструкция blade/ripper из состояния, а не из ввода.** Blade OFF опаздывает на +2…+11 кадров. Обратите внимание: окно бифуркации (`rAnim 12→151`, i≈540–600) начинается сразу после задержанных blade-OFF на кадрах 518→520 и 545→556. То есть **главная бифуркация record↔playback, скорее всего, прямое следствие этой задержки** — это фикс №1.
3. **Обратная связь через камеру.** `m_fInputDirection` проецируется на камеру; дрейф курса → дрейф follow-камеры → та же `InputUnit` интерпретируется иначе → усиление дрейфа. Это объясняет, почему курс расходится первым.

## Что можно сделать, оставаясь во вводе

### 1. Фикс точности записанного ввода (приоритет №1, чисто input)

Перестать реконструировать blade/ripper из `blade_mode_type`/`ripper_enabled` и писать в кадр **сам факт нажатия**:

- При старте записи разрезолвить keybind→VK через `ms_aKeyMap` (`base+0x14CD838`), затем каждый кадр сэмплировать `ms_KeyInput.m_aKeysDown` (удержание blade, keybind 8) и `m_aKeysPressed` (фронт ripper, keybind 11) — вы уже читаете их в `hooks::read_keys()`.
- Добавить в `ReplayFrame` 1–2 байта флагов (`blade_down`, `ripper_pressed`).
- В `playback_tick` вести `BLADE_HOLD`/`RIPPER_FRAMES` прямо из этих флагов, а не из `state`.

Это убирает +2…+11 кадров и, вероятно, основную бифуркацию. Заодно уйдут 14/899 расхождений бита `0x800` (маркер blade) — они следствие, а не причина.

### 2. Выравнивание временных условий записи и воспроизведения (ввод не трогаем)

Сейчас record и playback живут на разных последовательностях dt (record=51.7, playback=52.6–56.2) — даже идеально детерминированная игра разъедется. Варианты по возрастанию инвазивности:

- **Внешний/встроенный лок FPS** (RTSS, vsync, или busy-wait-пейсер в начале `render()`), одинаковый для записи и воспроизведения. Это не модификация состояния игры — только темп кадров. Ожидание: playback↔playback → ~0, record↔playback → уровень остаточного шума таймера.
- **Запись реального покадрового dt и воспроизведение темпа.** Сейчас покадровый `duration_ms` фиктивный (`frame_index*1000/60`). Писать реальную дельту `Instant` между кадрами; в playback подавать кадр N не сразу, а когда накопленная сумма dt записи достигнута. На той же машине темп воспроизводим. Это даёт dt-идентичность без вмешательства в код игры.

### 3. Замкнутая коррекция самим вводом (руление)

Если остаточный дрейф мал, его можно гасить, не выходя за пределы ввода:

- **Курс/камера** — `right_stick`: П-регулятор по ошибке `recorded.rot.y − current.rot.y` в мёртвой зоне ±ε, 1–3 кадра. Камера — прямой канал (дельта мыши), и возврат камеры одновременно чинит проекцию `input_direction`.
- **Позиция** — `left_stick` (pure pursuit: целиться в точку записи на k кадров вперёд; масштаб 1000 даёт аналоговый контроль скорости).
- **Фазовая подстройка** — если расхождение выглядит как сдвиг по времени (игрок «опаздывает»), можно офлайн сдвигать индексы последующих кадров на оценённый фазовый сдвиг, а не менять значения.

Ограничения честные: коррекция не должна вмешиваться возле скриптовых/критических событий (climb, blade-переходы) — там она сама станет источником бифуркации; после ветвления состояния (разный `rAnim`, другая геометрия) ввод уже не возвращает траекторию — только предотвращение дрейфа до точки.

### 4. TAS-воркфлоу вместо живой коррекции

Для speedrun-практики часто надёжнее: короткие сегменты с отложенным стартом по триггеру (у вас уже есть), чекпоинты-триггеры посередине (при расхождении выше порога — стоп и ре-arm), итеративная перезапись проблемных окон. У вас есть покадровый state-лог — добавьте офлайн-компаратор record↔playback (pos/rot/rAnim/blade/ripper по кадрам), чтобы находить **первый** кадр расхождения, а не следствие.

## Что вне «только ввод», если этого не хватит

Из вашего же списка митигаций, как эскалация:

- **(b) подмена дельты анимации на константу 1/60** — гарантирует детерминизм, но это уже хук времени игры, не ввод;
- **(c) snap-коррекция позиции/курса** и **(d) ресинк по rAnim** — прямая запись в состояние, для чистого TAS неприменимы, годятся как отладочный инструмент.

## Рекомендуемый порядок действий

1. Фикс записи blade-hold/ripper-pressed (§1) — закрывает известную бифуркацию.
2. Лок FPS (одинаковый при записи и воспроизведении) + замерить playback↔playback.
3. Реальный покадровый dt в БД + воспроизведение темпа (§2).
4. Офлайн-компаратор и первый кадр расхождения — решать по его природе: если снова критическое событие — чекпоинт/перезапись; если медленный дрейф — руление (§3) или пункт (b).

Ключевой вывод: при текущей архитектуре главный выигрыш дают не алгоритмы коррекции, а устранение двух уже найденных дефектов — реконструкции blade и разного темпа кадров записи/воспроизведения. Остаток после них, судя по вашим цифрам, будет порядка метров→сантиметров, и вот его уже можно докрывать рулением через стики.
