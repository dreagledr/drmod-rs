# API автоматизации drmod-rs (HTTP + скрипты + логи)

Дизайн-документ интерфейса автоматизированного общения с игрой (Metal Gear Rising: Revengeance) для человека и LLM: запуск скриптов ввода, чтение состояния, получение логов персонажа по временному интервалу.

> **Статус:** Этап 1 (HTTP-сервер + запуск скрипта + кольцевой буфер логов) — реализован. Формат скрипта и эндпоинты зафиксированы ниже; изменения — только через этот документ.

---

## 1. Цель и принятые решения

**Цель:** дать внешнему клиенту (человек через `curl`, LLM-агент, скрипт) возможность:

1. **Запускать скрипты ввода** — последовательности действий (бег, прыжок, атаки, камера, ripper, blade) с таймингами в кадрах.
2. **Читать текущее состояние** игры — миссия, статус меню, позиция/HP/анимация/состояния персонажа.
3. **Получать логи персонажа по временному интервалу** — per-frame снимки, чтобы понять результат скрипта.

**Зафиксированные решения:**

| Вопрос | Решение |
|--------|---------|
| Транспорт | **HTTP REST** на `127.0.0.1:5223` (собственный минимальный сервер на `TcpListener`), JSON-запросы/ответы |
| Формат скриптов | **JSON-массив команд**, тайминги в **кадрах** (60 FPS) |
| Логи по интервалу | **Кольцевой буфер в памяти** (последние ~60 сек), `GET /logs` |
| Доступность | **Debug и release** (подача ввода/скрипты — общий код, не `#[cfg(debug_assertions)]`) |
| Набор входов | Базовый: `forward`, `jump`, `light_attack`, `heavy_attack`, `camera`, `ripper`, `blade` |
| История прогонов | Только кольцевой буфер; SQLite **не** используется для скриптов |
| Порт | `5223` (мультиплеерный TCP/UDP — `5222`, не конфликтует) |

**Почему HTTP:** самый простой транспорт для LLM и человека — `curl`/`fetch`, читаемый JSON, без клиентских библиотек. Shared memory/named pipe требуют клиента-обёртки и не дают выигрыша на частоте запросов, которая нужна автоматизации (поллинг состояния — единицы Гц).

**Почему кадры, а не миллисекунды:** подача ввода в игре идёт строго по кадрам (1 кадр на тик, см. `docs/REPLAY.md` §4.3). Кадры — TAS-стандарт и точны; мс при нестабильном FPS (52–58) дают дрейф.

## 2. Архитектура

```
┌─────────────────────────── процесс игры (32-bit) ───────────────────────────┐
│                                                                             │
│  render-цикл (hudhook, ~60 Гц)                                              │
│  ├─ read_game_state() → UiState                                             │
│  ├─ read_current_input() / read_player_state() / read_camera_state()        │
│  ├─ api.frame_update(...)                                                   │
│  │    ├─ продвижение активного скрипта → set_input_override()               │
│  │    │   + hooks::set_ripper_frames / set_blade_hold                       │
│  │    ├─ запись кадра в кольцевой буфер (с script_id)                       │
│  │    └─ обновление снимка /state                                           │
│  └─ NumPad4 → api.start_builtin_script()  (тот же механизм, что и HTTP)     │
│                                                                             │
│  HTTP-поток (TcpListener, 127.0.0.1:5223)                                   │
│  └─ обработчики: /health /state /script/* /logs                             │
│       └─ читают Arc<Mutex<SharedState>> (буфер, скрипт, снимок)             │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
        ▲
        │ HTTP (JSON)
        ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  Клиент: curl / LLM-агент / скрипт                                          │
└─────────────────────────────────────────────────────────────────────────────┘
```

**Потокобезопасность:** `SharedState` (кольцевой буфер, активный скрипт, снимок) — в `Arc<Mutex<>>`. Render-поток пишет (короткие критические секции, 60 Гц), HTTP-поток читает. Подача ввода — через существующий глобальный `replay::set_input_override` (static `Mutex<InputOverride>`), который читает детур `updateInputUnit` в игровом тике.

**Жизненный цикл:**
- **Старт:** `ApiServer` создаётся в `HelloHud::new()` — bind `127.0.0.1:5223`, запуск потока.
- **Loading (рестарт/меню):** активный скрипт **автоматически останавливается** (override снимается) — иначе залипший ввод сломает пересоздающийся игрок (см. `docs/REPLAY_FINDINGS.md`).
- **Eject (выгрузка DLL):** перед `hudhook::eject()` вызывается `api.shutdown()` — stop-флаг + join потока + снятие override. Поток — неблокирующий accept с опросом флага (10 мс) и таймауты read/write (1 с) на каждом соединении, поэтому join гарантированно завершается за ограниченное время; внутренних потоков (как у tiny_http) нет — выгрузка DLL безопасна.

## 3. Эндпоинты

Базовый URL: `http://127.0.0.1:5223`

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/health` | Живость, версия, base_addr |
| GET | `/state` | Текущий снимок игры + статус скрипта + fps + текущий t_ms |
| POST | `/script/run` | Запустить скрипт (JSON-тело) |
| POST | `/script/stop` | Остановить активный скрипт |
| GET | `/script/{id}` | Статус скрипта по id |
| GET | `/logs` | Кадры из кольцевого буфера (фильтры: `from_ms`, `to_ms`, `script_id`, `limit`) |
| POST | `/eject` | Выгрузить DLL (ставит флаг → render-цикл выполняет eject) |

Ошибки: HTTP-код + JSON `{ "error": "..." }` с человекочитаемым текстом (на русском, как UI).

### 3.1. `GET /health`

```json
{
  "status": "ok",
  "version": "0.1.0",
  "base_addr": "0x00400000",
  "uptime_ms": 123456
}
```

### 3.2. `GET /state`

```json
{
  "t_ms": 123456,
  "mission_id": 272,
  "mission_name": "R-01",
  "menu_status": "InGame",
  "player": {
    "found": true,
    "pos": [-24.7, 12.1, 120.7],
    "rot": [0.0, 1.57, 0.0],
    "vel": [0.0, 0.0, 0.0],
    "hp": 100,
    "r_anim": 0,
    "ripper": 0,
    "blade": 0
  },
  "camera": {
    "pos": [-24.7, 12.1, 120.7],
    "look_at": [-24.7, 12.1, 119.7],
    "rot": [1.5708, 0.0, 0.0]
  },
  "script": {
    "id": 1,
    "name": "run-jump-attack",
    "status": "running",
    "frame": 45,
    "total_frames": 130
  },
  "fps": 58.2
}
```

- `t_ms` — монотонная шкала от старта мода; используется как база для `from_ms`/`to_ms` в `/logs`.
- `script` — `null`, если скрипт не запускался или завершился.
- `menu_status` — строка из `game::GameMenuStatus::name()`.

### 3.3. `POST /script/run`

Тело — скрипт (формат в §4). Ответ:

```json
{
  "script_id": 1,
  "name": "run-jump-attack",
  "total_frames": 130
}
```

Ошибки:
- `400` — невалидный JSON / неизвестный вход / пустой `commands` / тайминги вне диапазона (текст ошибки указывает конкретное поле).
- `409` — уже запущен другой скрипт (`{ "error": "script already running: id=1 name=..." }`).

### 3.4. `POST /script/stop`

Останавливает активный скрипт: снимает override и blade-hold, статус → `stopped`.

```json
{ "stopped": true, "script_id": 1 }
```

Если активного скрипта нет — `404` `{ "error": "no active script" }`.

### 3.5. `GET /script/{id}`

```json
{
  "id": 1,
  "name": "run-jump-attack",
  "status": "running",
  "frame": 45,
  "total_frames": 130
}
```

`status`: `running` | `done` | `stopped`. Неизвестный id — `404`.

### 3.6. `GET /logs`

Возвращает кадры из кольцевого буфера. Параметры (все опциональны):

| Параметр | Тип | По умолчанию | Описание |
|----------|-----|--------------|----------|
| `from_ms` | int | 0 | Начало интервала (включительно), шкала `t_ms` |
| `to_ms` | int | сейчас | Конец интервала (включительно) |
| `script_id` | int | — | Только кадры, записанные во время этого скрипта |
| `limit` | int | 1000 | Максимум кадров в ответе (защита от гигантских ответов) |

```json
{
  "from_ms": 0,
  "to_ms": 5000,
  "count": 300,
  "frames": [
    {
      "t_ms": 0,
      "frame": 0,
      "script_id": 1,
      "pos": [-24.7, 12.1, 120.7],
      "rot": [0.0, 1.57, 0.0],
      "vel": [0.0, 0.0, 0.0],
      "hp": 100,
      "r_anim": 0,
      "ripper": 0,
      "blade": 0,
      "camera_pos": [-24.7, 12.1, 120.7],
      "camera_look_at": [-24.7, 12.1, 119.7],
      "camera_rot": [1.5708, 0.0, 0.0],
      "input": { "buttons": ["forward"], "left_stick": [0.0, -1000.0], "right_stick": [0.0, 0.0] }
    }
  ]
}
```

- `input.buttons` — **декодированные имена** активных кнопок (`forward`, `jump`, `light_attack`, `heavy_attack`), а не hex-битмаски — LLM-дружелюбно.
- Кадры, записанные во время активного скрипта, помечены его `script_id` → `GET /logs?script_id=N` возвращает **именно результат скрипта N** (позиция/HP/анимация по кадрам).
- Кадры вне скрипта — `script_id: null`.

### 3.7. `POST /eject`

Выгрузка DLL (эквивалент кнопки «Выход / Выгрузить DLL» в UI). Тело не требуется.

```json
{ "ejecting": true }
```

**Механизм:** HTTP-поток **только ставит флаг** в `SharedState` и успевает ответить. Render-цикл проверяет флаг каждый кадр и выполняет ту же последовательность, что и кнопка: отключение сети → `api.shutdown()` (stop-флаг + join HTTP-потока + снятие override ввода) → `hudhook::eject()`. Вызов eject из HTTP-потока невозможен: `shutdown()` джойнит сам себя (deadlock), а `hudhook::eject()` обрабатывается в render-цикле после Present. Кнопка «Выход / Выгрузить DLL» в UI ставит тот же флаг (`ApiServer::request_eject()`) — единый путь выгрузки.

**Поведение после eject:**
- API перестаёт отвечать (порт 5223 освобождается) — клиент должен учитывать: таймауты на запросы, повторный инжект для продолжения работы.
- Идемпотентно: повторный `POST /eject` до обработки флага тоже возвращает `200`; после обработки соединения отклоняются.
- Активный скрипт останавливается (override снимается в `shutdown()`), как при обычном eject.

## 4. Формат скрипта

Скрипт — JSON-объект с именем и массивом команд. **Каждая команда — «включить такие-то входы с кадра `t` на `duration` кадров».** Скрипт завершается, когда истекли все команды.

```json
{
  "name": "run-jump-attack",
  "commands": [
    { "t": 0,  "duration": 60, "input": { "forward": true, "left_stick": [0, -1000] } },
    { "t": 45, "duration": 2,  "input": { "jump": true } },
    { "t": 85, "duration": 2,  "input": { "light_attack": true } },
    { "t": 95, "duration": 35, "input": { "camera": [300, 0] } }
  ]
}
```

### 4.1. Поля команды

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `t` | int ≥ 0 | да | Кадр от старта скрипта (0-based), когда команда активируется |
| `duration` | int ≥ 1 | да | Сколько кадров команда активна |
| `input` | объект | да | Набор входов (см. ниже) |

### 4.2. Входы (`input`)

| Ключ | Тип | Семантика |
|------|-----|-----------|
| `forward` | bool | Движение вперёд (W): бит `0x400000` + `left_stick = [0, -1000]` |
| `backward` | bool | Движение назад (S): бит `0x800000` + `left_stick = [0, 1000]` |
| `left` | bool | Движение влево (A): бит `0x200000` + `left_stick = [-1000, 0]` |
| `right` | bool | Движение вправо (D): бит `0x100000` + `left_stick = [1000, 0]` |
| `jump` | bool | Прыжок (Space): бит `0x10` + фронт `pressed=0x10` на первом кадре. **Высота зависит от длительности удержания**: 1 кадр ≈ 1.7 м, 15 кадров ≈ 2.1 м, 40–45 кадров (весь подъём) ≈ 2.8 м = полная высота (как ручной). Двойного прыжка (второе нажатие в воздухе) нет (тесты +2…+30 кадров). Бит `0x1` — кнопка меню оружия, НЕ прыжок |
| `light_attack` | bool | Лёгкая атака (ЛКМ): бит `0x40`, down + pressed на первом кадре |
| `heavy_attack` | bool | Тяжёлая атака (ПКМ): бит `0x80`, down + pressed на первом кадре |
| `camera` | `[dx, dy]` | Поворот камеры: `right_stick = [dx, dy]` (дельта мыши, реальный диапазон сотни–тысячи, до ~±6500) на каждый кадр команды. ⚠️ Чувствительность низкая: по оси Y значения <~500 камеру не двигают (порог игры) — используйте ≥1000 |
| `ripper` | bool | Ripper (toggle): фронт `isKeybindPressed(11)` на первом кадре команды; `duration` игнорируется (флаг живёт ровно 1 игровой тик). 🔧 Фикс 2026-08-18: счёт ведётся в `script_tick` (сброс в начале кадра), а не декрементом в детуре — игра вызывает `isKeybindPressed(11)` спорадически (disable/ enable-проверки на разных кадрах), счётчик «растекался» на несколько переключений. ✅ проверено: вкл/выкл чисто, на бегу держится. Второй путь активации — биты InputUnit `0x1000`/`0x8000` (консольные L3+R3: down одного + pressed другого) |
| `blade` | bool | Blade mode (hold): бит `0x800` в `buttons_down` (удержание) + **фронт `pressed=0x800` на первом кадре** команды (вход в состояние) — как `ninja_run` (0x4000). 🔧 Фикс 2026-08-18: keybind-эмуляция `isKeybindDown(8)` НЕ работает — игра читает её только в key-event обработке (0x61DA85), скрипт key events не создаёт; реальный ввод кодирует блейд битом 0x800 (запись 33 в БД: `down=00400800` + фронт). Механизм — как в playback (replay.rs) |
| `ninja_run` | bool | Ниндзя-бег: бит `0x4000` в `buttons_down` (удержание) + **фронт `pressed=0x4000` на первом кадре** команды (вход в состояние). `isKeybindDown(9)` для unit 0 игра не читает. ✅ проверено (r_anim=71, ~7.9 у/с на открытом участке) |
| `walk` | bool | Медленный шаг: `left_stick` масштабируется ×0.5 (игра кодирует ходьбу магнитудой стика: ручная ходьба даёт `L=(0,-500)`, `r_anim=2`; keybind 4 игра не читает — дизассемблирование 2026-08-18) |
| `dodge` | bool | Уклонение (Z, hold): удержание `isKeybindDown(21)` |
| `lock_on` | bool | Lock-on (E, toggle): удержание `isKeybindDown(12)` на все кадры команды ⚠️ не проверено (нужен враг) |
| `subweapon` | bool | Под-оружие (C): удержание `isKeybindDown(13)` на все кадры ⚠️ не проверено |
| `item` | bool | Предмет (Q): удержание `isKeybindDown(14)` на все кадры ⚠️ не проверено |
| `ar_mode` | bool | AR-режим (1): сырая клавиша в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `weapon_select` | bool | Меню выбора оружия (2): сырая клавиша в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `codec` | bool | Меню кодек (3): сырая клавиша в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `zandatsu` | bool | Zandatsu (X): удержание `isKeybindDown(20)` на все кадры ⚠️ не проверено (нужен враг) |
| `camera_reset` | bool | Сброс камеры (СММ): удержание `isKeybindDown(19)` на все кадры ⚠️ не проверено |
| `pause` | bool | Пауза/меню (Esc): сырая клавиша в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `confirm` | bool | Подтвердить в меню (Enter): сырая клавиша в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `menu_up` / `menu_down` / `menu_left` / `menu_right` | bool | Стрелки в меню: сырые клавиши в кэш `ms_KeyInput` ⚠️ механизм НЕ работает (см. §10.3) |
| `left_stick` | `[x, y]` | Явный стик (переопределяет дефолт движения) |

Неизвестные ключи в `input` — ошибка `400` (защита от опечаток LLM: `"light_attackk"` не пройдёт молча).

### 4.3. Семантика вычисления кадра

На кадре `K` скрипт собирает `InputUnit` из всех активных команд (`t <= K < t + duration`):

1. Движение (`forward`/`backward`/`left`/`right`) → `buttons_down |= бит направления`; `left_stick` собирается из направлений (`[0,-1000]`/`[0,1000]`/`[-1000,0]`/`[1000,0]`, диагонали суммируются), если `left_stick` не задан явно.
2. `jump`/`light_attack`/`heavy_attack` → `buttons_down |= бит`; на `K == t` — также `buttons_pressed |= бит` (однократный фронт).
3. `camera` → `right_stick = [dx, dy]`.
4. Hold-действия (`dodge`) → `hooks::set_keybind_hold(keybind, true)` на время команды; при окончании — `false`. Работает (отдельные call sites `isKeybindDown`). Проверено: `dodge`. Исключения: `walk` — keybind 4 игра не читает, ходьба = стик ×0.5 (см. §4.2); `ninja_run`/`blade` — биты InputUnit `0x4000`/`0x8000` + фронт pressed на первом кадре (keybind-путь для unit 0 не работает).
5. Toggle-действия (`lock_on`/`subweapon`/`item`/`camera_reset`/`zandatsu`) → `hooks::set_keybind_hold(keybind, true)` на время команды — ⚠️ **не работает** (цикл 5..22 в 0x61DE21 не влияет на unit 0, см. §10.3). Исключение — `ripper`: `hooks::set_keybind_pressed(11, 1)` (единственное действие через `isKeybindPressed`).
6. Меню-клавиши и цифры 1/2/3 (`pause`/`ar_mode`/`weapon_select`/`codec`/`confirm`/`menu_*`) → запись сырой клавиши в кэш `ms_KeyInput` + заморозка `ms_bUpdateKeyboard` — ⚠️ **не работает** (DirectInput перезаписывает кэш, см. §10.3). План: хук `isKeyDown`/`isKeyPressed`.
7. Если хоть что-то активно — `valid_input = 1`, override активен; иначе — override снят (реальный ввод проходит).

### 4.4. Валидация

- `commands` не пустой.
- `t >= 0`, `duration >= 1`, `t + duration <= 3600` (максимум 60 сек при 60 FPS).
- `input` содержит хотя бы один известный ключ.
- `camera` — ровно 2 числа.
- `name` — строка ≤ 64 символа (опционально, по умолчанию `"script"`).

### 4.5. Встроенный скрипт NumPad4

NumPad4 запускает тот же механизм, что и `POST /script/run`, со встроенным скриптом «run-jump-attack» (бег ~1 сек → прыжок на бегу → лёгкий удар → поворот камеры) — ровно текущее поведение `update_input_injection` (`src/tas/replay.rs`), но через общий `ScriptRunner`.

## 5. Кольцевой буфер

- Ёмкость: **3600 кадров** (60 FPS × 60 сек). При переполнении старые кадры вытесняются.
- Кадр пишется в `render()` каждый кадр, когда игрок читаем (`player_found`).
- Кадр содержит: `t_ms` (монотонная шкала от старта мода), `frame` (счётчик render-кадров), `script_id` (активного скрипта или `null`), полный `PlayerState` + `CameraState` + `InputUnit` (декодированный в имена кнопок).
- `GET /logs` фильтрует по `t_ms`/`script_id` и ограничивает `limit`.

**Почему не SQLite:** скрипт-прогоны — короткоживущие и нужны сразу после запуска; флаш в БД (как у record/playback) добавляет задержку и не нужен для «понять результат скрипта». SQLite остаётся для сегментов и record/playback.

---

## 6. Безопасность и ограничения

- **Bind только `127.0.0.1`** — API недоступен снаружи машины. Токен не нужен (локальный интерфейс).
- **Лимит тела запроса: 64 КБ** — защита от гигантских скриптов.
- **Один активный скрипт** — повторный `POST /script/run` → `409`.
- **Авто-стоп при loading** — вход в меню/рестарт останавливает скрипт и снимает override (критично для безопасности: залипший ввод ломает пересоздающегося игрока).
- **Авто-стоп при eject** — `api.shutdown()` перед выгрузкой DLL: stop-флаг + join HTTP-потока (ограничен таймаутами сокетов) + снятие override.
- **`POST /eject`** — выгрузка DLL по запросу: HTTP-поток ставит флаг, render-цикл выполняет `shutdown()` + eject. После этого API недоступен до повторного инжекта.
- **Максимальная длительность скрипта** — 3600 кадров (60 сек).

## 10. Известные проблемы (2026-08-18)

### 10.1. Прыжок (бит `0x1`) открывает меню выбора оружия вместо прыжка — РЕШЕНО (2026-08-18)

**Симптом:** при подаче `jump` (бит `0x1` в `buttons_down`/`buttons_pressed`) в скрипте вместо прыжка открывается меню выбора оружия (`GameMenuStatus::SelectWeaponMenu`), персонаж замирает — ввод перехватывается меню. Меню также **навигирует по слотам** (при тесте селектор переехал со слота 1 на слот 4).

**Решение (эмпирически, 2026-08-18):** настоящий бит прыжка — **`0x10`** (ручной прыжок: `cur_in down=00000010 pressed=00000010` + `space=true`, y поднимается). Бит `0x1` — кнопка меню выбора оружия, не прыжок. `input_bits::JUMP` исправлен на `0x10`. Гипотеза о линейном маппинге `1 << keybind = 0x20` не подтвердилась.

**Длительность удержания (проверено):** высота прыжка зависит от того, сколько кадров держится бит `0x10` (Space): 1 кадр ≈ 1.7 м, 5 ≈ 1.7 м, 15 ≈ 2.1 м, 40–45 (весь подъём ~30 кадров) ≈ 2.8 м — полная высота, совпадает с ручными прыжками (11 прыжков по 2.80–2.84 м). **Двойного прыжка нет** (второе нажатие в воздухе на +2…+30 кадров не даёт прибавки высоты; ручные прыжки — одиночные параболы).

### 10.2. Краш/зависание при выгрузке DLL (eject) — РЕШЕНО (2026-08-18)

**Симптом:** при нажатии «Выход / Выгрузить DLL» игра виснет (или крашится).

**Причина (две, обе в tiny_http):**
1. **Бесконечный `join()` в `shutdown()`.** HTTP-поток мог навсегда заблокироваться в клиентском I/O: `request.respond()` (клиент не читает ответ) или чтение тела (клиент прислал `Content-Length`, но не дослал тело). tiny_http не выставляет таймауты на сокетах (`ServerConfig` содержит только `addr` и `ssl`), поэтому `handle.join()` в `shutdown()` виснул навсегда → render-поток замирал.
2. **Неуправляемые внутренние потоки tiny_http.** `Server::new` порождает accept-поток, 4 вечных worker'а `TaskPool` (ждут на condvar без таймаута) и поток на каждое соединение. Все они выполняют код, слинкованный в DLL, и не джойнятся (`Server::drop` только ставит флаг `close`). При `FreeLibraryAndExitThread` они оставались живыми на выгруженном коде → краш.

**Решение:** tiny_http заменён на собственный минимальный HTTP-сервер (паттерн `net.rs` — «разбудить блокирующий вызов + join»):
- Один поток, неблокирующий `accept()` + опрос stop-флага каждые 10 мс — `shutdown()` будит поток мгновенно.
- `set_read_timeout`/`set_write_timeout` (1 с) на каждом соединении — клиент не может заблокировать поток навсегда, `join()` ограничен.
- `Connection: close` на каждый ответ — без keep-alive, висящих соединений нет.
- Внутренних потоков нет — все потоки наши и джойнятся в `shutdown()`.

**Верификация:** `cargo build` (debug+release) без ошибок; eject с открытым соединением (браузер/curl keep-alive) и с зависшим клиентом — игра выгружает DLL без зависания.

### 10.3. Меню-клавиши (стрелки/Enter/Esc) — raw-подача через кэш НЕ работает, нужен хук `isKeyDown`/`isKeyPressed`

**Механизм (дизассемблирование, 2026-08-18):** стрелки/Enter **не являются keybind'ами** (нет в `eSaveKeybind`) — меню читает их через `KeyInput::isKeyDown`/`isKeyPressed` (0x9D93A0/0x9D9400, **thiscall**) из кэша `ms_KeyInput`. Маппинг: `isKeyDown(vKey)` читает `ms_KeyInput.m_aKeysDown[vKey>>5] & (0x80000000 >> (vKey & 31))`; эквивалентно REPLAY.md маппингу (`игровой код = VK ^ 0x1F`, `bit = 1 << (code & 31)`).

**Что было испробовано (2026-08-18):**
1. **Запись в кэш `ms_KeyInput` + заморозка `ms_bUpdateKeyboard=false`** (`hooks::set_raw_key` → `apply_raw_keys` в детуре `updateInputUnit`) — **НЕ работает**: `ms_bUpdateKeyboard=0` ставится (заморозка видна), но `ms_KeyInput` остаётся 0 при активной подаче — DirectInput перезаписывает кэш независимо от флага (или меню читает ввод напрямую). `pause`/`confirm`/`menu_*` — не подтверждены (в тестах меню открывал/закрывал пользователь своим esc).
2. **Keybind-эмуляция** (`isKeybindDown(18)` для pause, `isKeybindDown(16)` для weapon_select) — **НЕ работает**: цикл 5..22 (0x61DE21, сборка констант/полей в `[esp+0x4C]`) не влияет на активный unit 0. Работает только для действий с отдельными call sites (dodge 21, ninja 9, движение 1/2/3, execution 20).

**Следующий шаг (план):** хук `isKeyDown` (0x9D93A0) и `isKeyPressed` (0x9D9400) — детур `extern "C" fn(vKey: i32) -> i32` (this в ECX игнорируется): для эмулируемых клавиш (битмаски `RAW_KEYS_*`) возвращает 1; иначе читает `ms_KeyInput` напрямую (как оригинал) — оригинальный trampoline не вызываем (thiscall, this в ECX не передаётся). Коды — VK: Esc `0x1B`, Enter `0x0D`, стрелки `0x26`/`0x28`/`0x25`/`0x27`, цифры `0x31`/`0x32`/`0x33`. Подача: удержание на duration + фронт pressed на первом кадре.

**Побочный эффект (устар. для кэш-механизма):** на время подачи raw-клавиш кэш клавиш замораживался — реальный ввод игрока с клавиатуры не обновлялся (keybind-эмуляция скрипта при этом работает — детуры не зависят от кэша). При переходе на хук `isKeyDown`/`isKeyPressed` заморозка не нужна.

### 10.4. Camera: `right_stick[1]` (pitch/наклон) — низкая чувствительность (2026-08-18)

**Симптом (тест `camera: [300,0]` / `[0,200]`, P118_BEACH):** `right_stick[0]` (yaw) — камера поворачивается ✅; `right_stick[1]` (pitch) при `[0,200]` — наклона нет ❌. Значение `(0,200)` видно в `/logs` (`input.right_stick`), т.е. подача доходит до `m_CurrentInput`, но камера не реагирует.
