## 1. Факты (количественно)

### 1.1. FPS-гипотеза не подтверждается

- Длительности кадров record == playback **побайтово** (1021 кадр, 16–17 мс,
  0 кадров > 25 мс) — стабильные 60 FPS, дропов нет.
- `frame_duration_ms` в CSV — накопленное время (elapsed), прирост ~16.7 мс/кадр.

### 1.2. Лаг подачи ввода = ровно 1 кадр у ВСЕХ playback

- `play[fi] == rec[fi-1]` на **100.0%** кадров (лаг 0 — 18.7%), для всех 78/81/82.
- Природа: `playback_tick` выставляет override в `render(K)`, игра применяет его
  на тике K+1 (`update_input_unit_detour` в `hooks.rs`). Документировано в коде.
- Сдвиг начинается с fi=26–27 — с первого ненулевого ввода.

### 1.3. Недетерминизм при идентичном вводе

- Ввод у 78/81/82 **полностью идентичен** (все 12 полей InputUnit, все 1021 кадров);
  стартовые условия (pos/hp/r_anim) тоже.
- При этом playback'и расходятся **между собой**: 78↔82 — до **17.0 м**,
  78↔81 — до 1.6 м; `r_anim` расходится с fi=170 (78 vs 81) и fi=233 (78 vs 82).
- Вывод: недетерминизм — в самой игре (фаза Present↔тик), а не в подаваемом вводе.

### 1.7. Стики vs кнопки

- Сдвиг на 1 кадр одинаково затрагивает и кнопки, и стики.
- **Стики** (камера): медленный самокомпенсирующийся дрейф — у 82 на fi=249–258
  |Δpos| даже *уменьшался* (0.42→0.31). Большой диапазон значений сам по себе
  не ломает воспроизведение.
- **Кнопки** (дискретные фронты): критичны, когда сдвинутый фронт попадает в
  **переключение анимационного автомата** (вход в ninja run, атаки) — дают
  необратимые «переломы» траектории.

## 2. Варианты уменьшения отклонения

### Вариант A — компенсация лага ✅ РЕАЛИЗОВАН (2026-08-23)

Подавать `frame[frame_idx + 1]` вместо `frame[frame_idx]` в `playback_tick`:
тик N записи имел ввод `frame[N]`; воспроизведение сейчас применяет `frame[N]`
на тике N+1. Со сдвигом индексации тик N+1 применит `frame[N+1]` — фазы сойдутся.

- `frame[0]` записи — нулевой ввод спавна (кадры 0–2 пустые), потеря безвредна.
- Реализация: в `src/tas/replay.rs::playback_tick` — гейт `frame_idx + 1 < len`,
  доступ `frames[frame_idx + 1]`; лог кадра — `frame_idx + 1`.
- **Результат (record 87 → 88/89/90):** лаг 0 = 100% (было 18.7%), лучший прогон
  88 — макс |Δpos| 2.7 м (было ~17 м), r_anim совпадает до fi=533. НО
  недетерминизм сохранился: 89/90 разошлись до 16.5/25.3 м (приземления мимо
  зон по высоте), playback↔playback при идентичном вводе — до 25 м.
- Вывод: лаг — один из источников, но фазовая неопределённость Present↔тик
  осталась → вариант B.

### Вариант B — подача в детур (синхронно с тиком) ✅ РЕАЛИЗОВАН (2026-08-23)

Выдавать следующий кадр прямо в `update_input_unit_detour` (в тике, для
`user_index == 0`), а не из render. Каждый тик получает ровно один кадр ввода
**в том же тике** — лаг исчезает, фаза Present перестаёт влиять.

- Реализация: `replay::PLAYBACK_FEED` (static `Mutex<PlaybackFeed{frames, next_idx, done}>`) —
  заполняется при старте (`start_playback_feed`), очищается при стопе
  (`clear_playback_feed`); детур вызывает `replay::feed_playback(unit)` вместо
  `apply_override` (fallback на обычный override для API-скриптов/debug — при
  пустом буфере). Кадры предобрабатываются один раз при старте (`prepare_frame`:
  weapon_select gate + конвертация raw-клавиш меню в D-Pad биты) — детур только
  копирует. `next_idx = 1`: `frames[0]` (нулевой ввод спавна) не подаётся —
  компенсация та же, что в варианте A. `playback_tick` теперь только логирует
  результат и останавливает воспроизведение при `done`.
- **Результат (record 91 → 92/93/94/95, 1054 кадра, длины совпали):**
  | Прогон | Оценка | макс \|Δpos\| | r_anim vs record |
  |---|---|---|---|
  | 92 | фейл | 16.5 м | расходится с ~550 |
  | 93 | фейл | 17.1 м | расходится с ~550 |
  | 94 | частичный (платформа) | 1.96 м | редкие сдвиги +1..+5 |
  | **95** | **успех** | **0.91 м** | **совпадает до конца** |
  - Лаг 0 = 100%, прыжки 13/13 фронтов на тех же кадрах у всех.
  - 95 — лучший результат за всю работу: |Δpos| < 0.9 м, along +0.04 м
    (отставания нет), курсовой угол 0.5°. 94: «мелкая платформа» пропущена —
    переход на fi≈624 задержан на +5 кадров (≈0.8 м продольного смещения).
  - Недетерминизм НЕ устранён полностью: 92/93 vs 94/95 расходятся до 16 м при
    идентичном вводе. Фаза Present убрана — остался **внутренний недетерминизм
    игры**: момент входа в ninja run (fi 194 vs 195) и редкие анимационные
    сдвиги ±1..+5 кадров. Прыжки сами по себе идеальны — ломается точность
    приземления в плоскости (горизонтальный дрейф к критическим зонам).

### Вариант D — дубль кадра ввода (продление hold) ✅ РЕАЛИЗОВАН, ОТКЛЮЧЁН (2026-08-23)

Где playback отстаёт вдоль движения (`along < 0`), можно подать текущий кадр
повторно (не инкрементировать `next_idx`) — персонаж проходит ещё одно смещение
кадра по вектору и догоняет запись. Безопасно только в hold-окнах.

**Анализ по record 91 (`tools/desync_analysis/analyze6_hold.py`):**
- Hold-окна (условие: `down` стабилен, нет фронтов `pressed`/`released`,
  left_stick константен, анимация — движение; правый стик можно менять):
  **118 кадров (11.2%), 27 сегментов**, среднее смещение за кадр 0.111 м.
- Дубль = «лишний» тик движения → +0.11–0.16 м вдоль вектора.
- Модель компенсации (дубль в кадре с отставанием >2 см, интервал 3):
  | Прогон | Отставание (среднее/макс) | Дублей доступно | Выигрыш | После компенсации |
  |---|---|---|---|---|
  | 94 | 0.52 / 1.57 м | 24 | 3.17 м | **отставание >5 см не осталось** |
  | 95 | 0.11 / 0.39 м | 11 | 1.43 м | **отставание >5 см не осталось** |
  | 92 | 2.99 / 16.3 м | 18 | 2.38 м | ~8.4 м (необратимо) |
  | 93 | 2.79 / 16.7 м | 19 | 2.38 м | ~7.4 м (необратимо) |
- Вывод: для «близких» прогонов (94/95) дубли полностью убирают продольное
  отставание; фейлы (92/93) после срыва не лечатся.
- Реализация: render (`playback_tick`) считает `along`-ошибку (текущая позиция
  vs записанная `state.pos` подаваемого кадра; направление — разность позиций
  поданного и следующего кадров); при `along < −0.15 м` и безопасном hold
  (`should_dup_frame`: down стабилен, нет фронтов в ближайшие 5 кадров, стик
  движения отклонён, анимация ∈ бег/ninja run/ходьба) ставит `DUP_REQUESTED`;
  детур `feed_playback` при флаге подаёт кадр повторно (без инкремента).
  Ограничения: не чаще 1 дубля на 3 кадра подачи, лимит 30 дублей на прогон
  (сброс при старте). Лог `playback: frame dup at idx N` в debug.log.
- Верификация: `cargo build --release` + `cargo clippy --all-targets` — без новых
  предупреждений. **Рантайм-тест (record 96 → 97/98/99/100): механика работает,
  исход не меняет.** Дубли сработали только в фейлах (98/99 — по 4 шт при
  отставании >0.15 м); хорошие прогоны (97/100) не отставали вдоль — дублей 0,
  при этом 97 vs 100 при идентичном вводе расходятся на 2 м (внутренний
  недетерминизм). Визуально: дубль перед прыжком продлевал движение → ПЕРЕЛЁТ
  (прыжок слишком далеко). **D отключён (`DUP_ENABLED = false`);** для включения
  — подобрать пороги (`DUP_LAG_THRESHOLD`, `DUP_SAFE_AHEAD`) и запрет дублей
  в окне перед прыжком.
- Риск: дубль продлевает движение по текущему направлению — компенсирует только
  продольную компоненту; боковая (perp) остаётся → вариант E.

### Вариант E — поправка камеры стиком (компенсация курса) ✅ РЕАЛИЗОВАН (2026-08-23)

Отклонение курса/камеры компенсируется добавкой к `right_stick`: поворот камеры
в MGR:R относительно свободен, персонаж движется относительно камеры.

**Чувствительность (`tools/desync_analysis/analyze7_stick.py`, консистентно на
record 73 и 91):**
- `right_stick_x = 1000` → Δyaw ≈ **−0.62…−0.73°** за кадр;
- `right_stick_y = 1000` → Δpitch ≈ **−0.51…−0.70°** за кадр;
- ≈ 0.0006–0.0007 °/ед/кадр; задержка стик→камера ~1 кадр (корреляция k=1
  сильнее: r ≈ −0.50); авто-поворот при rsx=0 — 0.04–0.11°/кадр.
- Поправка: `delta_rsx ≈ −dYaw / 0.00065` (1° → ~1600 ед. на 1 кадр, или ~400 ед.
  на 4 кадра). Отклонения yaw у 94/95: медиана 1.2–2.2°, макс ~10°.
- Ограничения: это поворот камеры, поворот тела следует плавно — коррекцию
  растягивать на 3–6 кадров и делать частичной (50–70%), иначе перекоррекция;
  шум (r ≈ −0.25…−0.5) — сглаживать dYaw.
- Реализация: render (`playback_tick`) считает dYaw (текущий `cam_yaw` из
  CameraState vs записанный в кадре `PLAYBACK_FEED`), при `|dYaw| > 0.5°`
  ставит поправку `delta_rsx = −dYaw / 0.00065 · 0.6` (клэмп ±2000) в
  `PLAYBACK_FEED.rsx_correction`; детур `feed_playback` добавляет её к
  `right_stick_x` следующего поданного кадра (один раз, обнуляется).
  Лог `playback: cam correction rsx=… (dYaw …°)`. Порог/усиление/клэмп —
  константы `CAM_THRESHOLD_RAD`/`CAM_GAIN`/`CAM_CLAMP`.
- **Баг при старте (прогон 101): камеру разворачивало на 180°.** Причины:
  (1) эталоном был БУДУЩИЙ кадр (`next_idx`) — при активной коррекции эталон
  «уезжал» вместе с поворотом, dYaw не сходился → раскрутка; (2) коррекция
  работала при |dYaw| до 180° (старт/спавн камера смотрит «не туда»).
  **Фикс:** эталон — последний ПОДАННЫЙ кадр (`next_idx - 1`); коррекция
  только при |dYaw| < 90° (`CAM_MAX_CORRECT_RAD`).
- **Баг знака (прогон 104: поворот на ~90° влево в начале).** `corr` имел знак
  «минус», но в записи **положительный rsx поворачивает камеру ВЛЕВО** (record
  104: rsx 1400–6600 → dYaw −2…−4°/кадр). При dYaw > 0 (камера правее записи)
  минус давал rsx < 0 → камера уезжала ещё правее → dYaw рос до ~125° (пока
  < 90° коррекция крутила, дальше — оставалась развёрнутой). **Фикс: знак
  «плюс»** (`corr = +dyaw / SENS · GAIN`) — коррекция теперь УСИЛИВАЕТ
  записанный поворот, а не противодействует ему.
- **Результат (record 110 → 111/112/113/114): 4/4 успех.**
  | Прогон | макс \|Δpos\| | \|Δyaw\| медиана | \|Δcam_pos\| макс | along среднее |
  |---|---|---|---|---|
  | 111 | 1.03 м | 0.12° | 0.35 м | +0.015 м |
  | 112 | 0.70 м | 0.18° | 0.24 м | +0.019 м |
  | 113 | 0.95 м | 0.26° | 0.71 м | +0.044 м |
  | 114 | 0.89 м | 0.16° | 0.66 м | +0.039 м |
  - Камера «в струе»: |Δyaw| медиана 0.12–0.26° (было 0.5–1.1° в B),
    доля кадров >1° — 1.1–1.5% (было 25–95%). Отставания вдоль нет
    (along > 0 у всех). r_anim совпадает, прыжки 13/13 на тех же кадрах.
    Playback↔playback 0.87–1.36 м (было 16–25 м).
  - лаг 0 = 93–96% — не 100% из-за поправок E к `right_stick_x` (ожидаемо).
  - **Вывод: связка B (подача в детур) + E (компенсация курса) даёт
    воспроизводимость ~1 м при 4/4 успешных прогонах.** Остаточный разброс —
    внутренний недетерминизм игры; против него только snap-коррекция (C).
- Верификация: `cargo build --release` + `cargo clippy --all-targets` — без новых
  предупреждений.

### Вариант C — snap-коррекция по позиции (гибрид, если A/B/D/E не хватит)

Периодически при `perp` > порога плавно корректировать позицию игрока к записи
(прямая запись pos — механизм есть, NumPad1). Удерживает траекторию, но это уже
не «чистое» воспроизведение ввода.

### Проверка результата (после каждого варианта)

1. Записать record + 3 playback (NumPad5/6, arm → рестарт R-01).
2. `dbdump <record_id> --out <dir>` → CSV.
3. `tools/desync_analysis/analyze*.py <dir>`:
   - лаг 0/1/2 (должен стать лаг 0 при A/B);
   - playback↔playback (должны сойтись при B);
   - первый fi >0.5 м, along/perp, углы, камера.
4. `plot_cam.py <dir> <out.png>` — график.

## 3. Скрипты (`tools/desync_analysis/`)

| Скрипт | Что делает |

| `analyze2.py` | лаг 0/1/2 ввода, точка устойчивого роста |Δpos|, смены r_anim |

| `analyze6_hold.py` | hold-окна (безопасный дубль кадра) и модель компенсации отставания |
| `analyze7_stick.py` | чувствительность right_stick → cam_yaw/pitch (°/ед/кадр, задержка) |

Все скрипты принимают каталог с CSV первым аргументом (дефолт
`C:\temp\dbdump_out_release`), затем `REC_ID PLAY_ID...` (у analyze6/7 — только
record); `plot_cam.py` — второй аргумент путь PNG.
Запуск: `py -3 tools/desync_analysis/analyze.py [DIR] [REC_ID PLAY_ID...]`.
