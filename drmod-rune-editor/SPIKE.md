# Spike: can Rune carry the TAS editor?

The question behind this crate. The shipping editor already proves that ImGui can do a dock space,
a 20 000-row table and a code editor at once. Rune offers a different trade: plain-Rust views,
live theming and motion, but no dock space and a general text field instead of a code editor. This
spike measures the three hard things in that stack and records where it stops.

Environment: Linux, `x86_64-unknown-linux-gnu`, headless Rune (`--snap` / `--tree`), window
1440×900 points, Rune `dev` @ `0c8a62e7`. Rune's headless default is scale 2 (2880×1800 pixels),
so the scale is named in each number; `--scale 1` is the 1440×900-pixel case. Numbers are Rune's
own headless frame report (`frame cpu`, which is update + build + encode/submit, without a real
present).

## The three hard things

### 1. A 20 000-frame table

Fixtures: 200 frame lines at 100-frame spacing, projected by
`drmod_script::projection::project` into 19 901 rows. The table is `rune_kit::Table`: only the
visible rows are built, sorting is off, columns resize, the header is sticky.

| Build | Scale | Frame CPU p50 | p95 |
|---|---|---|---|
| release | 1× | **2.33–2.40 ms** | 4.9 ms |
| release | 2× | **2.5–2.7 ms** | 7.7–8.0 ms |
| debug | 2× | 8.2 ms | 15.4 ms |

The same release run on the 173-frame `alpha2` script (174 rows) had the same p50: the table's
virtualisation does what it says. Scrolling the 20 000-row table in a scripted debug run stayed in the same range
(9.6 ms p50). The idle (at-rest) figure is 1.7 ms at 1× and 2.3 ms at 2×.

A 240-frame headless run of *either* script also contains a one-time ~100 ms frame at 1× and a
~360 ms frame at 2×. It is not the table — the small script has it too — and it scales with pixels,
so it reads as headless pipeline/atlas setup rather than the editor's steady state.

The number that is *not* flat is the first display of the text. Opening a 201-line / 20 000-frame
script in a 1.5 s scripted run at 1× produced a 200 ms frame; the 7-line script produced 35 ms.
That cost is not the projection: measured on the same text in release, parsing is 0.07 ms,
`projection::project` 0.45–1.5 ms for 19 901 rows, and writing the JSON 0.2 ms. It is Rune laying
out and shaping the whole 201-line text in `TextArea`; `TextArea` has no virtual lines. A production
editor would need to avoid that stall (split the text into virtual lines, or debounce the initial
layout), and typing in a multi-thousand-line script is the next measurement to make.

### 2. The text editor

Rune's `TextArea` is a rich text field, not a code editor. The spike uses it in a kit whose `ty.ui`
is the mono face, with per-frame `Span`s from a small `.tas` lexer:

- comments, the `!` rules line, its `name=`/`trig=`/`restart` attributes, values, frame numbers,
  the six stick tokens and every button token colour correctly, including UTF-8 byte offsets
  (tested with Cyrillic comments);
- typing, selection, undo, IME, focus and the caret are Rune's;
- `Ctrl+S` is handled by the field's own `on_key` and by the window's `on_key`, so it works while
  typing;
- scrolling is internal to `TextArea` (its height is fixed to the pane and the caret is kept in
  view).

What is missing compared with `dear-imgui-cte`:

- **wrapping instead of horizontal scroll** — long `.tas` lines wrap;
- **no gutter and no line numbers**; a gutter would have to be a second column synced to the
  text's wrapped layout, which Rune does not expose;
- **no language-aware editing keys** (toggle comment, bracket matching, autocomplete);
- **no syntax-aware selection**.

Typing into a 200-line script stayed responsive. The long fixture is the counter-example:
`examples/stress-long.tas` (4 018 lines, 399 901 frames, generated by `tools/make-stress.py`) took
~320 ms to open at 1×, held a steady p50 of 2.56–2.67 ms, and each edit added roughly 180–250 ms
of CPU over a 360-frame run (the mean delta against the same run without the edit). That is
`TextArea` laying out the whole text again, not the projection: parsing this file is 2.4 ms and
`projection::project` is 18–29 ms for 399 901 rows. Typing in a multi-thousand-line script is
therefore not interactive; a code area with virtual lines is the fix, and it is a feature in its
own right rather than a tweak.

### 3. The layout

`rune_kit::shell::SplitView` gives a resizable sidebar, a main pane and an inspector, with a
toolbar and a title-bar inset. The frames table is a vertical split added by hand: a 7 pt drag
handle storing its own height, clamped against the body's measured height in `on_layout_tx`.

This is not a dock space. Panels cannot float, be re-docked, or be rearranged into tabs; the
author gets one split layout. Headless `--tree` confirmed the geometry and no zero-height scroll
viewport after the table was given a bounded parent.

## What else works

- the workspace: folder picker (`native-file-dialog`, XDG portal on Linux), listing, buffers,
  dirty markers, save, new / duplicate / rename / delete (rename and delete in `Dialog`s);
- the run path, verified against a mock mod: `GET /state` twice, then `POST /dt`, `/fps`, `/rng`,
  `/script/run` in that order, with the seed last; `409` retried after `/script/stop`; the menu
  settler runs before the levers;
- the status poll every 500 ms, the game panel, the run message, the Stop button;
- light and dark themes, both snapshotted; settings persisted in the same file the ImGui editor
  uses on Windows.

## What the spike says

**Rune is viable for a lean TAS editor.** The table, the colouring, the split layout and the API
work; a release build keeps a 19 900-row table at a p50 of 2.3–2.7 ms of CPU per frame, which is
well inside a 60 Hz budget. The first display of a 200-line script is the outlier (~200 ms at 1×),
and a 4 000-line stress script is ~320 ms to open and ~200 ms per edit, because `TextArea` has no
virtual lines. The result looks like a desktop app rather than a demo.

**It is not yet a drop-in replacement for the ImGui editor.** The missing code editor (wrapping,
gutter, code keys), the missing dock space, and `TextArea`'s whole-text layout on open and on every
edit are real product differences. Porting further means either accepting a leaner editor for
realistic scripts (tens of lines) or building a code area (gutter + horizontal viewport + virtual
lines) on top of Rune's text primitives — a project of its own.

The experiment stops here with a working editor and a measured answer, not with a shipping
replacement.
